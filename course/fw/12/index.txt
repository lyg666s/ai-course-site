<h2 id="开发和测试的顺序">开发和测试的顺序</h2>
<ol>
<li><strong>TLD</strong>：Test-Last Development，开发先行，测试后行</li>
<li><strong>TDD</strong>：Test-Driven Development，测试先行，开发后行</li>
</ol>
<h2 id="测试选型">测试选型</h2>
<ul>
<li><strong>单元测试</strong>：屏蔽外部，测试单函数、类</li>
</ul>
<p>目录建议：<code>unit/</code></p>
<p>适用场景：复杂或重要的函数、类</p>
<ul>
<li><strong>集成测试</strong>：多模块、类、函数的交互</li>
</ul>
<p>目录建议：<code>integration/</code></p>
<p>适用场景：核心，达到测试覆盖率的核心手段</p>
<ul>
<li><strong>系统测试</strong>：测试整个真实运行的系统</li>
</ul>
<p>目录建议：<code>e2e / system</code></p>
<p>适用场景：必做，通常是测试真实环境的启动是否会带来新问题，走一些happy path即可</p>
<ul>
<li><strong>e2e测试</strong>：在系统测试的基础上，测试某个业务功能链（一个用例跑完整个功能链）</li>
</ul>
<p>目录建议：<code>e2e</code></p>
<p>适用场景：必做，主要业务功能链</p>
<ul>
<li><strong>冒烟测试</strong>：系统的底线/红线/生命线，冒烟测试未通过可视为灾难性事故</li>
</ul>
<p>目录建议：<code>不限</code></p>
<p>适用场景：下面的情况满足任意一条，必须设置为冒烟测试
  - <strong>如果这个功能挂了，用户立刻无法完成核心任务</strong></p>
<div class="codehilite"><pre><span></span><code>登录挂了→用户进不来；下单挂了→收不到钱；支付回调挂了→钱付了但订单没更新
</code></pre></div>

<ul>
<li>
<p><strong>这个功能被90%以上的用户每天使用</strong></p>
<p>比如“查看商品详情”是电商的高频功能，而“修改收货地址”相对低频</p>
</li>
<li>
<p><strong>这个功能是其他所有功能的前置依赖</strong></p>
<p>比如“获取用户Token”是所有需要登录接口的前提，如果它挂了，后面几十个接口都测不了</p>
</li>
<li>
<p><strong>这个功能一旦出错，会造成严重的数据损失或资损</strong></p>
<p>比如“扣减库存”不能多扣，“退款”不能多退，这类功能哪怕使用频率不高也要加冒烟</p>
</li>
<li>
<p><strong>这个功能历史上经常出问题（痛点回归）</strong></p>
<p>某个接口特别容易改坏（比如复杂的计算逻辑），即使它不算最核心，也可以加冒烟作为“保险”</p>
</li>
</ul>
<blockquote>
<p>[!IMPORTANT]</p>
<p>冒烟测试往往不针对新功能，而是已上线、稳定运行一段时间的旧功能</p>
</blockquote>
<h2 id="测试手段">测试手段</h2>
<h3 id="Stub-模式">Stub 模式</h3>
<div class="codehilite"><pre><span></span><code><span class="c1"># 假设这是你的业务代码（app/services/sms.py）</span>
<span class="k">class</span><span class="w"> </span><span class="nc">SmsService</span><span class="p">:</span>

<span class="c1"># app/routers/login.py</span>

        <span class="c1"># 后续其他逻辑</span>
</code></pre></div>

<h3 id="Mock-模式">Mock 模式</h3>
<div class="codehilite"><pre><span></span><code><span class="k">def</span><span class="w"> </span><span class="nf">test_login_with_mock</span><span class="p">(</span><span class="n">mocker</span><span class="p">):</span>
    <span class="c1"># 直接 patch 掉 SmsService 类</span>
    <span class="n">mock_sms_class</span> <span class="o">=</span> <span class="n">mocker</span><span class="o">.</span><span class="n">patch</span><span class="p">(</span><span class="s2">"app.services.sms.SmsService"</span><span class="p">)</span>

    <span class="n">mock_sms_class</span><span class="o">.</span><span class="n">return_value</span><span class="o">.</span><span class="n">send_verify_code</span><span class="o">.</span><span class="n">return_value</span> <span class="o">=</span> <span class="p">{</span><span class="s2">"code"</span><span class="p">:</span> <span class="mi">888888</span><span class="p">,</span> <span class="s2">"success"</span><span class="p">:</span> <span class="kc">True</span><span class="p">}</span>

    <span class="c1"># 调用</span>
    <span class="n">result</span> <span class="o">=</span> <span class="n">login</span><span class="o">.</span><span class="n">send_verify_code</span><span class="p">()</span>

    <span class="k">assert</span> <span class="n">result</span><span class="p">[</span><span class="s2">"code"</span><span class="p">]</span> <span class="o">==</span> <span class="mi">888888</span>
    <span class="k">assert</span> <span class="n">result</span><span class="p">[</span><span class="s2">"success"</span><span class="p">]</span> <span class="ow">is</span> <span class="kc">True</span>

    <span class="c1"># 验证：获取实例，再验证它的方法被调用了一次</span>
    <span class="n">mock_sms_class</span><span class="o">.</span><span class="n">return_value</span><span class="o">.</span><span class="n">send_verify_code</span><span class="o">.</span><span class="n">assert_called_once</span><span class="p">()</span>

<p>有些团队有硬性指标，比如测试覆盖率必须达到80%，否则无法PR</p>
