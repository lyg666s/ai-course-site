<h2 id="为什么需要测试">为什么需要测试</h2>
<h3 id="没有测试的困境">没有测试的困境</h3>
<p>在图书管理系统的开发过程中，如果我们不写测试，会面临以下问题：</p>
<div class="codehilite lang-mermaid"><pre><span></span><code>flowchart LR
    A[修改代码] --&gt; B{是否引入Bug？}
    B --&gt;|不知道| C[手动点击测试]
    C --&gt; D[只覆盖部分场景]
    D --&gt; E[上线后用户发现问题]

    style E fill:#ffcdd2
</code></pre></div>

<table>
<thead>
<tr>
<th>问题</th>
<th>说明</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>回归风险</strong></td>
<td>修改 A 功能，意外破坏了 B 功能，无法及时发现</td>
</tr>
<tr>
<td><strong>手动测试低效</strong></td>
<td>每次改动都要手动点击验证，耗时且容易遗漏</td>
</tr>
<tr>
<td><strong>信心不足</strong></td>
<td>不敢重构代码，因为不知道会不会改坏</td>
</tr>
<tr>
<td><strong>文档缺失</strong></td>
<td>测试用例本身就是最好的行为文档</td>
</tr>
</tbody>
</table>
<h3 id="自动化测试的价值">自动化测试的价值</h3>
<table>
<thead>
<tr>
<th>价值</th>
<th>说明</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>快速反馈</strong></td>
<td>修改代码后几秒内知道是否破坏了功能</td>
</tr>
<tr>
<td><strong>回归保障</strong></td>
<td>确保已修复的 Bug 不会重新出现</td>
</tr>
<tr>
<td><strong>支持重构</strong></td>
<td>有测试保护，可以放心重构</td>
</tr>
<tr>
<td><strong>行为文档</strong></td>
<td>测试描述了代码的预期行为</td>
</tr>
<tr>
<td><strong>降低调试成本</strong></td>
<td>问题在开发阶段被发现，而非生产环境</td>
</tr>
</tbody>
</table>
<h3 id="测试金字塔">测试金字塔</h3>
<p><strong>测试金字塔</strong>描述了不同类型测试的合理比例：</p>
<div class="codehilite lang-mermaid"><pre><span></span><code>flowchart TB
    A[端到端测试&lt;br/&gt;E2E Tests&lt;br/&gt;少量、慢、脆弱] --&gt; B[集成测试&lt;br/&gt;Integration Tests&lt;br/&gt;适中、中等速度]
    B --&gt; C[单元测试&lt;br/&gt;Unit Tests&lt;br/&gt;大量、快、稳定]

    style A fill:#ffcdd2
    style B fill:#fff3e0
    style C fill:#e8f5e9
</code></pre></div>

<table>
<thead>
<tr>
<th>层级</th>
<th>数量</th>
<th>速度</th>
<th>依赖</th>
<th>验证范围</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>单元测试</strong></td>
<td>最多</td>
<td>毫秒级</td>
<td>无（Mock）</td>
<td>单个类/方法</td>
</tr>
<tr>
<td><strong>集成测试</strong></td>
<td>适中</td>
<td>秒级</td>
<td>数据库、容器</td>
<td>多个组件协作</td>
</tr>
<tr>
<td><strong>端到端测试</strong></td>
<td>最少</td>
<td>分钟级</td>
<td>完整环境</td>
<td>完整业务流程</td>
</tr>
</tbody>
</table>
<blockquote>
<p>[!NOTE]
金字塔的核心思想：<strong>多写单元测试，少写端到端测试</strong>。单元测试快、稳定、容易定位问题；端到端测试慢、脆弱，但能验证整体流程。</p>
</blockquote>
<h3 id="测试驱动开发TDD简介">测试驱动开发（TDD）简介</h3>
<p><strong>TDD（Test-Driven Development）</strong> 是一种开发方法论，流程如下：</p>
<div class="codehilite lang-mermaid"><pre><span></span><code>flowchart LR
    A[写测试&lt;br/&gt;Red] --&gt; B[运行测试&lt;br/&gt;失败] --&gt; C[写代码&lt;br/&gt;Green] --&gt; D[重构&lt;br/&gt;Refactor] --&gt; A

    style A fill:#ffcdd2
    style C fill:#e8f5e9
    style D fill:#e3f2fd
</code></pre></div>

<table>
<thead>
<tr>
<th>阶段</th>
<th>说明</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>Red</strong></td>
<td>先写一个失败的测试，描述期望的功能</td>
</tr>
<tr>
<td><strong>Green</strong></td>
<td>写最少的代码让测试通过</td>
</tr>
<tr>
<td><strong>Refactor</strong></td>
<td>在测试保护下重构代码，改善设计</td>
</tr>
</tbody>
</table>
<blockquote>
<p>[!NOTE]
TDD 不是强制要求，但理解其思想有助于写出更好的测试。本课程不强制 TDD，但推荐在开发中先思考测试场景。</p>
</blockquote>

<h2 id="实战为-ISBN-校验工具类编写单元测试">实战：为 ISBN 校验工具类编写单元测试</h2>
<h3 id="需求">需求</h3>
<p>图书管理系统中需要校验 ISBN 格式。ISBN（国际标准书号）有两种格式：</p>
<ul>

<h3 id="6-测试执行速度">6. 测试执行速度</h3>
<p>单元测试应该非常快（毫秒级）。如果测试超过 1 秒，可能有以下问题：
- 做了 I/O 操作（读写文件、网络请求）
- 初始化了 Spring 上下文
- 使用了 <code>Thread.sleep()</code></p>

<h2 id="小结">小结</h2>
<p>本节课我们学习了：</p>
<ol>
<li><strong>测试的价值</strong>：快速反馈、回归保障、支持重构、行为文档</li>
<li><strong>测试金字塔</strong>：单元测试（多）、集成测试（适中）、端到端测试（少）</li>
<li><strong>Spring Boot 测试体系</strong>：<code>spring-boot-starter-test</code> 包含了 JUnit 5、Mockito、AssertJ 等</li>
<li><strong>JUnit 5 核心用法</strong>：
   - 核心注解：<code>@Test</code>、<code>@BeforeEach</code>、<code>@AfterEach</code>、<code>@BeforeAll</code>、<code>@AfterAll</code>
   - 断言方法：<code>assertEquals</code>、<code>assertTrue</code>、<code>assertThrows</code>、<code>assertAll</code>
   - 参数化测试：<code>@ParameterizedTest</code>、<code>@ValueSource</code>、<code>@CsvSource</code>、<code>@MethodSource</code></li>
<li><strong>实战应用</strong>：为 ISBN 校验工具类编写完整的单元测试</li>
</ol>
