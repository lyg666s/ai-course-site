<div class="codehilite lang-mermaid"><pre><span></span><code>flowchart TB

<h2 id="健康检查分组">健康检查分组</h2>
<h3 id="什么是健康检查分组">什么是健康检查分组</h3>
<p>默认情况下，<code>/actuator/health</code> 会聚合所有健康指示器。<strong>健康检查分组</strong> 允许按用途将指示器分组，暴露不同的端点。</p>
<div class="codehilite lang-mermaid"><pre><span></span><code>flowchart TB
    A[HealthEndpoint] --&gt; B[/actuator/health/]
    A --&gt; C[/actuator/health/liveness/]
    A --&gt; D[/actuator/health/readiness/]

    B --&gt; E[所有指示器]
    C --&gt; F[仅 ping]
    D --&gt; G[db + redis + 自定义]

    style C fill:#e3f2fd
    style D fill:#e8f5e9
</code></pre></div>

<h3 id="为什么需要分组">为什么需要分组</h3>
<p>在 Kubernetes 等容器编排平台中：</p>
<table>
<thead>
<tr>
<th>检查类型</th>
<th>用途</th>
<th>分组</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>存活检查（Liveness）</strong></td>
<td>应用是否存活，失败则重启 Pod</td>
<td><code>/health/liveness</code></td>
</tr>
<tr>
<td><strong>就绪检查（Readiness）</strong></td>
<td>应用是否准备好接收流量，失败则摘除</td>
<td><code>/health/readiness</code></td>
</tr>
</tbody>
</table>
<p><strong>存活检查</strong>应该只检查应用本身（ping），不应包含外部依赖。<strong>就绪检查</strong>应包含所有依赖（数据库、缓存等）。</p>

<div class="codehilite lang-java"><pre><span></span><code><span class="kd">private</span><span class="w"> </span><span class="kt">boolean</span><span class="w"> </span><span class="nf">checkStockService</span><span class="p">()</span><span class="w"> </span><span class="p">{</span>

</code></pre></div>

<p>重新启动，访问 <code>/actuator/health</code>：</p>
<div class="codehilite lang-json"><pre><span></span><code><span class="p">{</span>
<span class="w">    </span><span class="nt">"status"</span><span class="p">:</span><span class="w"> </span><span class="s2">"DOWN"</span><span class="p">,</span>

这就是分组的价值：虽然就绪检查为 <code>DOWN</code>（不接收流量），但存活检查仍为 <code>UP</code>（不重启容器）。</p>
</blockquote>
<h2 id="注意事项">注意事项</h2>
<h3 id="1-健康指示器的性能">1. 健康指示器的性能</h3>
<p>健康检查会被频繁调用（如每秒多次），检查逻辑应尽量快：</p>
<table>
<thead>
<tr>
<th>检查项</th>
<th>建议</th>
</tr>
</thead>
<tbody>
<tr>
<td>数据库</td>
<td>使用 <code>isValid()</code> 而非复杂查询</td>
</tr>
<tr>
<td>外部 API</td>
<td>设置超时（如 1 秒）</td>
</tr>
<tr>
<td>磁盘</td>
<td>无开销</td>
</tr>
</tbody>
</table>
<h3 id="2-健康检查不应有副作用">2. 健康检查不应有副作用</h3>
<p>健康检查应该是只读操作，不应修改数据或触发业务逻辑。</p>
<h3 id="3-存活检查-vs-就绪检查">3. 存活检查 vs 就绪检查</h3>
<table>
<thead>
<tr>
<th>检查</th>
<th>包含内容</th>
<th>失败后果</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>Liveness</strong></td>
<td>只包含应用本身（ping）</td>
<td>容器被重启</td>
</tr>
<tr>
<td><strong>Readiness</strong></td>
<td>包含所有依赖</td>
<td>从负载均衡中摘除</td>
</tr>
</tbody>
</table>
<blockquote>
<p>[!CAUTION]
存活检查不要包含外部依赖。如果数据库挂了，存活检查失败会导致容器不断重启，反而加重问题。</p>
</blockquote>
<h3 id="4-避免过多的业务健康检查">4. 避免过多的业务健康检查</h3>
<p>业务健康检查失败会导致整个应用健康状态为 <code>DOWN</code>。对于非关键业务，建议：
- 使用自定义状态（如 <code>DEGRADED</code>）
- 或不纳入健康检查</p>
<h3 id="5-状态码的-HTTP-映射">5. 状态码的 HTTP 映射</h3>
<p>默认 <code>DOWN</code> 返回 503，如果与负载均衡器或其他系统约定不一致，需要配置：</p>
<div class="codehilite lang-yaml"><pre><span></span><code><span class="nt">management</span><span class="p">:</span>
<span class="w">  </span><span class="nt">endpoint</span><span class="p">:</span>
<span class="w">    </span><span class="nt">health</span><span class="p">:</span>
<span class="w">      </span><span class="nt">status</span><span class="p">:</span>
<span class="w">        </span><span class="nt">http-mapping</span><span class="p">:</span>
<span class="w">          </span><span class="nt">DOWN</span><span class="p">:</span><span class="w"> </span><span class="l l-Scalar l-Scalar-Plain">500</span>
</code></pre></div>

<h2 id="小结">小结</h2>
<p>本节课我们学习了：</p>
<ol>
<li><strong>健康检查机制</strong>：
   - <code>HealthIndicator</code> 接口
   - 健康状态（UP、DOWN、OUT_OF_SERVICE、UNKNOWN）
   - 聚合规则</li>
<li><strong>内置健康指示器</strong>：
   - <code>DataSourceHealthIndicator</code>、<code>DiskSpaceHealthIndicator</code>、<code>PingHealthIndicator</code></li>
<li><strong>自定义健康指示器</strong>：
   - 实现 <code>HealthIndicator</code>
   - 继承 <code>AbstractHealthIndicator</code>
   - 检查业务健康</li>
<li><strong>健康检查分组</strong>：
   - 存活检查（liveness）与就绪检查（readiness）</li>
<li><strong>实战应用</strong>：为图书管理系统添加缓存、库存服务、图书数据健康检查</li>
</ol>
