17:T12e1e,<h2 id="课程目标">课程目标</h2>
<ul>
<li>理解统一响应封装在前后端协作中的重要性</li>
<li>掌握统一响应类 <code>Result&lt;T&gt;</code> 的设计与使用</li>

<h2 id="为什么需要统一响应封装">为什么需要统一响应封装</h2>
<h3 id="现状问题">现状问题</h3>
<p>在之前的课程中，我们的 Controller 直接返回了 <code>Book</code> 对象或 <code>List&lt;Book&gt;</code>。这种方式的缺点：</p>
<table>
<thead>
<tr>
<th>问题</th>
<th>说明</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>格式不一致</strong></td>
<td>成功返回对象，失败返回 <code>Result.error</code>，前端需要分别处理不同格式</td>
</tr>
<tr>
<td><strong>缺少元信息</strong></td>
<td>无法返回业务状态码、时间戳等辅助信息</td>
</tr>
<tr>
<td><strong>错误信息不规范</strong></td>
<td>错误信息直接暴露给前端，缺乏统一格式</td>
</tr>
<tr>
<td><strong>前端处理困难</strong></td>
<td>每个接口的响应结构不同，需要为每个接口编写不同的处理逻辑</td>
</tr>
</tbody>
</table>
<h3 id="统一响应的好处">统一响应的好处</h3>
<div class="codehilite lang-mermaid"><pre><span></span><code>flowchart LR
    Frontend[前端] --&gt; API1[接口1&lt;br/&gt;统一格式]
    Frontend --&gt; API2[接口2&lt;br/&gt;统一格式]
    Frontend --&gt; API3[接口3&lt;br/&gt;统一格式]

    subgraph 后端
        API1
        API2
        API3
    end

    Frontend --&gt; Interceptor[统一拦截器]
    Interceptor --&gt; Error[统一错误处理]

    style Frontend fill:#e3f2fd
    style Interceptor fill:#e8f5e9
</code></pre></div>

<table>
<thead>
<tr>
<th>好处</th>
<th>说明</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>一致性</strong></td>
<td>所有接口返回相同结构，前端可以编写统一的数据处理逻辑</td>
</tr>
<tr>
<td><strong>可扩展性</strong></td>
<td>可以在响应中附加额外信息（时间戳、版本号、请求ID）</td>
</tr>
<tr>
<td><strong>错误处理统一</strong></td>
<td>前端根据固定的 <code>code</code> 字段判断请求是否成功</td>
</tr>
<tr>
<td><strong>便于监控</strong></td>
<td>统一的响应格式便于日志分析和系统监控</td>
</tr>
<tr>
<td><strong>便于文档生成</strong></td>
<td>Swagger 可以基于统一响应类生成一致文档</td>
</tr>
</tbody>
</table>
<h2 id="统一响应类设计">统一响应类设计</h2>
<h3 id="基本结构">基本结构</h3>
<p>一个标准的统一响应类通常包含以下字段：</p>
<table>
<thead>
<tr>
<th>字段</th>
<th>类型</th>
<th>说明</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>code</code></td>
<td><code>Integer</code></td>
<td>业务状态码（与 HTTP 状态码区分）</td>
</tr>
<tr>
<td><code>message</code></td>
<td><code>String</code></td>
<td>响应描述信息</td>
</tr>
<tr>
<td><code>data</code></td>
<td><code>T</code></td>
<td>响应数据（泛型）</td>
</tr>
<tr>
<td><code>timestamp</code></td>
<td><code>Long</code></td>
<td>响应时间戳（便于追踪）</td>
</tr>
<tr>
<td><code>path</code>（可选）</td>
<td><code>String</code></td>
<td>请求路径（便于调试）</td>
</tr>
<tr>
<td><code>success</code>（可选）</td>
<td><code>Boolean</code></td>
<td>是否成功（冗余字段）</td>
</tr>
</tbody>
</table>

</blockquote>
<h2 id="业务状态码设计">业务状态码设计</h2>
<h3 id="什么是业务状态码">什么是业务状态码</h3>
<p><strong>业务状态码</strong>是接口返回的用于表示业务处理结果的数字编码，不同于 HTTP 状态码。它让前端能够精确判断业务处理的具体情况，而不仅仅知道请求成功或失败。</p>
<h3 id="设计原则">设计原则</h3>
<table>
<thead>
<tr>
<th>原则</th>
<th>说明</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>分层分类</strong></td>
<td>按功能模块或错误类型分类，便于扩展</td>
</tr>
<tr>
<td><strong>语义清晰</strong></td>
<td>状态码本身能反映错误类型</td>
</tr>
<tr>
<td><strong>规范统一</strong></td>
<td>全系统使用同一套状态码规范</td>
</tr>
<tr>
<td><strong>可扩展</strong></td>
<td>预留状态码段供后续业务扩展</td>
</tr>
</tbody>
</table>
<h3 id="状态码分段设计">状态码分段设计</h3>
<table>

<tr>

<th>范围</th>
<th>含义</th>
</tr>

<td>200</td>
<td>请求成功</td>
</tr>
<tr>

<td>400-499</td>
<td>请求参数、格式、权限等问题</td>

<td>业务规则校验失败</td>
</tr>

</table>

<h2 id="HTTP-状态码与业务状态码的关系">HTTP 状态码与业务状态码的关系</h2>
<h3 id="两者的分工">两者的分工</h3>
<table>
<thead>
<tr>
<th>角色</th>
<th>HTTP 状态码</th>
<th>业务状态码</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>负责范围</strong></td>
<td>HTTP 协议层面的状态</td>
<td>业务层面的状态</td>
</tr>
<tr>
<td><strong>谁设置</strong></td>

<td>应用程序代码设置</td>

</tr>
</tbody>
</table>
<h3 id="两者的协作">两者的协作</h3>
<div class="codehilite lang-mermaid"><pre><span></span><code>flowchart TB
    Request[请求] --&gt; HTTP{HTTP 状态码}
    HTTP --&gt;|2xx| CheckBusiness{检查业务状态码}
    HTTP --&gt;|4xx/5xx| Error[网络/服务器错误]

    CheckBusiness --&gt;|code=200| Success[业务成功]
    CheckBusiness --&gt;|code≠200| BusinessError[业务错误]
    Success --&gt; Process[处理 data 数据]
    BusinessError --&gt; ShowError[显示错误信息]

    style HTTP fill:#e3f2fd
    style CheckBusiness fill:#fff9c4
</code></pre></div>

<p><strong>最佳实践建议：</strong></p>
<ul>
<li>HTTP 状态码用于判断请求是否<strong>到达并处理</strong>（网络、服务器、权限等）</li>
<li>业务状态码用于判断<strong>业务结果</strong>（数据是否正确、业务规则是否满足）</li>
<li>前端应<strong>优先检查业务状态码</strong>，因为 HTTP 状态码 200 不代表业务一定成功</li>
</ul>

<h2 id="全局异常处理">全局异常处理</h2>
<h3 id="ControllerAdvice-概述">@ControllerAdvice 概述</h3>
<p><code>@ControllerAdvice</code> 是 Spring 提供的统一异常处理注解，它可以让一个类成为全局的异常处理器，作用于所有 Controller。</p>
<table>
<thead>
<tr>
<th>注解</th>
<th>作用</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>@ControllerAdvice</code></td>
<td>全局异常处理 + 全局数据绑定 + 全局数据预处理</td>
</tr>
<tr>
<td><code>@RestControllerAdvice</code></td>
<td><code>@ControllerAdvice</code> + <code>@ResponseBody</code>，用于 REST API</td>
</tr>
</tbody>
</table>
<blockquote>
<p>[!NOTE]
推荐使用 <code>@RestControllerAdvice</code>，返回值自动转为 JSON。</p>
</blockquote>

<h2 id="注意事项">注意事项</h2>
<h3 id="1-业务状态码与-HTTP-状态码保持一致">1. 业务状态码与 HTTP 状态码保持一致</h3>
<p>在 RESTful API 中，建议业务状态码与 HTTP 状态码保持对应关系，避免混淆。例如，资源不存在时，HTTP 状态码和业务状态码都使用 404。</p>
<h3 id="2-成功不一定返回-200">2. 成功不一定返回 200</h3>
<p>创建资源成功应返回 201，删除成功返回 204。但这需要与前端团队提前约定。</p>
<h3 id="3-错误信息要友好">3. 错误信息要友好</h3>
<p>错误信息应包含足够的上下文，帮助前端定位问题，但不暴露系统内部细节。</p>
<h3 id="4-保持响应格式的一致性">4. 保持响应格式的一致性</h3>
<p>所有接口（包括错误）应使用相同的响应结构，避免前端判断逻辑复杂化。</p>
<h3 id="5-状态码枚举的维护">5. 状态码枚举的维护</h3>
<p>随着业务发展，状态码会不断增加。应定期整理和归档，避免状态码重复或含义模糊。</p>
<h2 id="小结">小结</h2>
<p>本节课我们学习了：</p>
<ol>
<li>
<p><strong>统一响应封装</strong>：使用 <code>Result&lt;T&gt;</code> 泛型类统一所有接口的响应格式。</p>
</li>
<li>
<p><strong>业务状态码设计</strong>：使用枚举 <code>ResultCode</code> 统一定义所有业务状态码。</p>
</li>
<li>
<p><strong>全局异常处理</strong>：</p>
</li>
</ol>
<ul>
<li>@RestControllerAdvice 统一处理异常</li>
<li>@ExceptionHandler 处理特定异常类型</li>
<li>统一返回 Result 响应格式</li>
</ul>
<ol start="4">
<li><strong>业务异常设计</strong>：</li>
</ol>
<ul>
<li>
<p>继承 RuntimeException 自定义异常</p>
</li>
<li>
<p>包含错误码，便于前端处理</p>
</li>
</ul>
