17:T8276,<h2 id="课程目标">课程目标</h2>
<ul>
<li>理解Nacos配置中心的三级模型（Namespace / Group / DataId），以及它与服务注册分级模型的异同</li>
<li>掌握DataId的默认构成规则（<code>prefix</code> - <code>profile</code> - <code>file-extension</code>）及各段的作用</li>
<li>掌握<code>spring.config.import</code>显式导入DataId、<code>shared-configs</code>共享配置、<code>extension-configs</code>扩展配置三种导入方式</li>
<li>理解多环境隔离的两种方案：Namespace隔离 vs DataId隔离，掌握各自的适用场景</li>
<li>完成book-product在dev/test两套环境下的DataId规划与验证</li>
<li>完成公共配置抽取，让book-product与book-user共享同一份数据源基础配置</li>
</ul>
<h2 id="回顾与导入">回顾与导入</h2>
<p>上一节完成了book-product的配置迁移：业务配置从本地<code>application.yml</code>搬到了Nacos的<code>book-product.yml</code>中，本地只保留接入配置。但这只是“一份配置”，还没有回答更复杂的问题：</p>
<blockquote>
<p><strong>场景一：环境区分。</strong> book-product同时有dev、test两套环境，它们的数据库连接不同、日志级别不同。是把配置拆成两份DataId，还是用Namespace隔离？</p>
<p><strong>场景二：配置共享。</strong> book-product和book-user使用同一个PostgreSQL实例、相同的连接池参数，如果每个服务各复制一份，未来改密码就要改N处。能不能把公共部分抽出来共享？</p>
<p><strong>场景三：本地调试覆盖。</strong> 开发人员本地调试时，希望临时覆盖Nacos中的某个配置，但又不想改动Nacos上的共享配置，应该怎么办？</p>
</blockquote>
<p>这三个问题的答案，都建立在Nacos配置中心的<strong>三级模型</strong>和<strong>DataId的匹配规则</strong>之上。本节先把模型讲清楚，再通过三个实战回答上述问题。</p>
<h2 id="配置中心的三级模型">配置中心的三级模型</h2>
<h3 id="三级模型回顾">三级模型回顾</h3>
<p>Nacos的分级存储模型是 <strong>Namespace → Group → DataId</strong> 三层结构。</p>
<div class="codehilite lang-mermaid"><pre><span></span><code>flowchart TB
    N[Nacos Server] --&gt; NS1[Namespace: dev]
    N --&gt; NS2[Namespace: test]
    NS1 --&gt; G1[Group: DEFAULT_GROUP]
    NS1 --&gt; G2[Group: BOOK_GROUP]
    G1 --&gt; D1[DataId: book-product.yml]
    G1 --&gt; D2[DataId: book-product-dev.yml]
    G1 --&gt; D3[DataId: common.yml]
    G2 --&gt; D4[DataId: book-order.yml]

    style D1 fill:#e8f5e9
    style D3 fill:#fff3e0
</code></pre></div>

<h3 id="定位唯一一份配置">定位唯一一份配置</h3>
<p>一份配置的完整定位由三个要素共同决定：</p>
<div class="codehilite"><pre><span></span><code>Namespace + Group + DataId  →  唯一一份配置
</code></pre></div>

<p>这意味着：</p>
<table>
<thead>
<tr>
<th>场景</th>
<th>是否会冲突</th>
</tr>
</thead>
<tbody>
<tr>
<td>不同Namespace下，相同的Group + DataId</td>
<td>不冲突，各自独立</td>
</tr>
<tr>
<td>同一Namespace下，不同Group，相同DataId</td>
<td>不冲突，各自独立</td>
</tr>
<tr>
<td>同一Namespace、同一Group下，相同DataId</td>
<td><strong>冲突</strong>，后发布的覆盖先发布的</td>
</tr>
</tbody>
</table>
<blockquote>
<p><strong>实践启示：</strong> 如果两个服务需要使用相同DataId的配置，又希望内容不同，隔离的维度只能是Namespace或Group——绝不能靠“在DataId里加前缀”这种临时手段，那样会破坏命名规范。</p>
</blockquote>
<h3 id="三级模型与配置匹配的关系">三级模型与配置匹配的关系</h3>
<p>Spring Cloud Alibaba在启动时，会按以下顺序尝试拉取配置：</p>
<div class="codehilite lang-mermaid"><pre><span></span><code>flowchart TB
    A[启动] --&gt; B[读取本地 application.yml]
    B --&gt; C[解析 spring.config.import]
    C --&gt; D[按 import 声明的 DataId 逐个拉取]
    D --&gt; E[解析 shared-configs]
    E --&gt; F[解析 extension-configs]
    F --&gt; G[合并配置，优先级：import &gt; 本地 &gt; shared &gt; extension]

    style D fill:#e8f5e9
</code></pre></div>

<h2 id="DataId的构成规则详解">DataId的构成规则详解</h2>
<h3 id="默认构成prefix---profile---extension">默认构成：prefix - profile - extension</h3>
<p>Spring Cloud Alibaba的默认DataId拼接规则是：</p>
<div class="codehilite"><pre><span></span><code>${prefix}-${spring.profiles.active}.${file-extension}
</code></pre></div>

</tr>

<tbody>

<td>无profile</td>
<td><code>book-product</code></td>
<td>无</td>
<td><code>yml</code></td>
<td><code>book-product.yml</code></td>
</tr>
<tr>
<td>dev环境</td>
<td><code>book-product</code></td>
<td><code>dev</code></td>
<td><code>yml</code></td>
<td><code>book-product-dev.yml</code></td>
</tr>
<tr>
<td>test环境</td>
<td><code>book-product</code></td>
<td><code>test</code></td>
<td><code>yml</code></td>
<td><code>book-product-test.yml</code></td>
</tr>
</tbody>
</table>
<h3 id="通过springconfigimport显式指定DataId">通过spring.config.import显式指定DataId</h3>
<p>上一节采用的写法是：</p>
<div class="codehilite lang-yaml"><pre><span></span><code><span class="nt">spring</span><span class="p">:</span>

</code></pre></div>

<p><strong>多DataId导入的写法：</strong></p>
<div class="codehilite lang-yaml"><pre><span></span><code><span class="nt">spring</span><span class="p">:</span>
<span class="w">  </span><span class="nt">config</span><span class="p">:</span>
<span class="w">    </span><span class="nt">import</span><span class="p">:</span>
<span class="w">      </span><span class="p p-Indicator">-</span><span class="w"> </span><span class="l l-Scalar l-Scalar-Plain">optional:nacos:book-product.yml</span>
<span class="w">      </span><span class="p p-Indicator">-</span><span class="w"> </span><span class="l l-Scalar l-Scalar-Plain">optional:nacos:common.yml</span>

<h3 id="DataId命名规范">DataId命名规范</h3>
<p>在图书系统中，建议遵循以下命名规范：</p>
<table>
<thead>
<tr>
<th>用途</th>
<th>命名</th>
<th>示例</th>
</tr>
</thead>
<tbody>
<tr>
<td>服务自身配置</td>
<td><code>${服务名}.yml</code></td>
<td><code>book-product.yml</code></td>
</tr>
<tr>
<td>服务+环境配置</td>
<td><code>${服务名}-${profile}.yml</code></td>
<td><code>book-product-dev.yml</code></td>
</tr>
<tr>
<td>公共配置</td>
<td><code>common-${作用域}.yml</code></td>
<td><code>common-datasource.yml</code></td>
</tr>
<tr>
<td>临时覆盖配置</td>
<td><code>${服务名}-${profile}-local.yml</code></td>
<td><code>book-product-dev-local.yml</code></td>
</tr>
</tbody>
</table>
<blockquote>
<p><strong>规范原则：</strong> 按“作用域从大到小”排列，公共配置放最前，服务配置居中，本地覆盖放最后。这样从DataId就能看出它的用途和覆盖关系。</p>
</blockquote>
<h2 id="多环境隔离的两种方案">多环境隔离的两种方案</h2>
<h3 id="方案一Namespace隔离推荐">方案一：Namespace隔离（推荐）</h3>
<p>同一DataId（如<code>book-product.yml</code>）在不同Namespace下是两份独立的配置：</p>
<div class="codehilite lang-mermaid"><pre><span></span><code>flowchart LR
    subgraph dev命名空间
        A1[book-product.yml&lt;br/&gt;dev数据库]
    end
    subgraph test命名空间
        B1[book-product.yml&lt;br/&gt;test数据库]
    end

    style A1 fill:#e8f5e9
    style B1 fill:#fff3e0
</code></pre></div>

<p><strong>配置方式：</strong></p>
<div class="codehilite lang-yaml"><pre><span></span><code><span class="nt">spring</span><span class="p">:</span>
<span class="w">  </span><span class="nt">cloud</span><span class="p">:</span>
<span class="w">    </span><span class="nt">nacos</span><span class="p">:</span>
<span class="w">      </span><span class="nt">config</span><span class="p">:</span>
<span class="w">        </span><span class="nt">namespace</span><span class="p">:</span><span class="w"> </span><span class="l l-Scalar l-Scalar-Plain">dev</span><span class="w">    </span><span class="c1"># dev环境实例用dev命名空间</span>
</code></pre></div>

<p><strong>优点：</strong></p>
<table>
<thead>
<tr>
<th>优点</th>
<th>说明</th>
</tr>
</thead>
<tbody>
<tr>
<td>数据完全隔离</td>
<td>不同Namespace的配置互不可见，误操作风险最低</td>
</tr>
<tr>
<td>数据ID一致</td>
<td>不用为每个环境维护不同的DataId命名</td>
</tr>
<tr>
<td>权限可独立控制</td>
<td>可按Namespace授权，生产环境只有特定人员能改</td>
</tr>
</tbody>
</table>
<p><strong>缺点：</strong> Namespace数量会随环境数量增长，如果环境很多（dev/test/staging/prod/多个项目组），管理成本会上升。</p>
<h3 id="方案二DataId隔离">方案二：DataId隔离</h3>
<p>所有环境共用同一Namespace，通过不同DataId区分：</p>
<div class="codehilite lang-mermaid"><pre><span></span><code>flowchart LR
    subgraph public命名空间
        A1[book-product-dev.yml]
        A2[book-product-test.yml]
        A3[book-product-prod.yml]
    end
</code></pre></div>

<p><strong>配置方式：</strong></p>
<div class="codehilite lang-yaml"><pre><span></span><code><span class="nt">spring</span><span class="p">:</span>
<span class="w">  </span><span class="nt">config</span><span class="p">:</span>
<span class="w">    </span><span class="nt">import</span><span class="p">:</span><span class="w"> </span><span class="l l-Scalar l-Scalar-Plain">optional:nacos:book-product-dev.yml</span>
</code></pre></div>

<p><strong>优点：</strong></p>
<table>
<thead>
<tr>
<th>优点</th>
<th>说明</th>
</tr>
</thead>
<tbody>
<tr>
<td>Namespace数量少</td>
<td>一个Namespace管所有环境</td>
</tr>
<tr>
<td>便于对比</td>
<td>在控制台一眼能看到所有环境的配置差异</td>
</tr>
</tbody>
</table>
<p><strong>缺点：</strong></p>
<table>
<thead>
<tr>
<th>缺点</th>
<th>说明</th>
</tr>
</thead>
<tbody>
<tr>
<td>数据未隔离</td>
<td>误操作（如改错DataId）的影响范围大</td>
</tr>
<tr>
<td>权限难细分</td>
<td>无法按环境隔离访问权限</td>
</tr>
<tr>
<td>DataId膨胀</td>
<td>N个环境 × M个服务 = N×M个DataId</td>
</tr>
</tbody>
</table>
<h3 id="两种方案的对比与推荐">两种方案的对比与推荐</h3>
<table>
<thead>
<tr>
<th>维度</th>
<th>Namespace隔离</th>
<th>DataId隔离</th>
</tr>
</thead>
<tbody>
<tr>
<td>数据隔离程度</td>
<td><strong>强</strong>（物理隔离）</td>
<td>弱（同Namespace）</td>
</tr>
<tr>
<td>权限控制</td>
<td>可按Namespace授权</td>
<td>难细分</td>
</tr>
<tr>
<td>管理成本</td>
<td>中（多Namespace）</td>
<td>高（多DataId）</td>
</tr>
<tr>
<td>误操作风险</td>
<td>低</td>
<td>较高</td>
</tr>
<tr>
<td>推荐场景</td>
<td><strong>生产、测试等长期环境</strong></td>
<td>临时验证、个人分支</td>
</tr>
</tbody>
</table>
<blockquote>
<p><strong>推荐组合：</strong> 生产、测试等长期环境用<strong>Namespace隔离</strong>；开发者个人调试用<strong>DataId隔离 + 本地覆盖</strong>（如<code>book-product-dev-local.yml</code>）。两种方案不互斥，可以按需组合。</p>
</blockquote>

<h2 id="shared-configs与extension-configs">shared-configs与extension-configs</h2>
<h3 id="为什么需要共享配置">为什么需要共享配置</h3>
<p>在上一节迁移方案中，每个服务都各自维护一份完整配置。但book-product和book-user之间存在大量重复配置：</p>
<table>
<thead>
<tr>
<th>重复配置项</th>
<th>内容</th>
</tr>
</thead>
<tbody>
<tr>
<td>数据源连接池参数</td>
<td><code>hikari.maximum-pool-size</code>、<code>connection-timeout</code>等</td>
</tr>
<tr>
<td>MyBatis-Plus全局配置</td>
<td><code>map-underscore-to-camel-case</code>、<code>id-type</code>等</td>
</tr>
<tr>
<td>日志通用配置</td>
<td><code>logging.level.root</code>等</td>
</tr>
</tbody>
</table>
<p>如果每个服务各复制一份，将来调整这些参数需要修改N处，很容易出现“某个服务忘了改”的不一致。</p>
<p><code>shared-configs</code>和<code>extension-configs</code>正是Nacos提供的两种“引入外部DataId”的机制。</p>
<h3 id="shared-configs共享配置">shared-configs：共享配置</h3>
<p><code>shared-configs</code>用于声明“多个服务共同使用的配置”，它是<strong>共享</strong>语义，优先级<strong>低于</strong>应用自身配置。</p>
<div class="codehilite lang-yaml"><pre><span></span><code><span class="p p-Indicator">-</span><span class="w"> </span><span class="l l-Scalar l-Scalar-Plain">optional:nacos:common-datasource.yml?group=DEFAULT_GROUP&amp;refreshEnabled=true</span>
<span class="p p-Indicator">-</span><span class="w"> </span><span class="l l-Scalar l-Scalar-Plain">optional:nacos:common-mybatis.yml?group=DEFAULT_GROUP&amp;refreshEnabled=true</span>
</code></pre></div>

<table>
<thead>
<tr>
<th>属性</th>
<th>说明</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>data-id</code></td>
<td>要共享的DataId</td>
</tr>
<tr>
<td><code>group</code></td>
<td>所在分组，默认<code>DEFAULT_GROUP</code></td>
</tr>
<tr>
<td><code>refresh</code></td>
<td>是否支持动态刷新，默认<code>false</code></td>
</tr>
</tbody>
</table>
<h3 id="extension-configs扩展配置">extension-configs：扩展配置</h3>
<p><code>extension-configs</code>用于声明“服务自身的额外配置”，优先级<strong>高于</strong><code>shared-configs</code>，但<strong>低于</strong>应用自身配置。</p>
<div class="codehilite lang-yaml"><pre><span></span><code><span class="p p-Indicator">-</span><span class="w"> </span><span class="l l-Scalar l-Scalar-Plain">optional:nacos:book-product-ext.yml?group=DEFAULT_GROUP&amp;refreshEnabled=true</span>
</code></pre></div>

<h3 id="三种配置源的优先级">三种配置源的优先级</h3>
<p>在配置生效优先级上，从高到低为：</p>
<div class="codehilite lang-mermaid"><pre><span></span><code>flowchart TB
    A[spring.config.import 显式导入] --&gt; B[应用自身 DataId&lt;br/&gt;book-product.yml]
    B --&gt; C[extension-configs]
    C --&gt; D[shared-configs]

    style A fill:#e8f5e9
</code></pre></div>

<h3 id="配置源选择">配置源选择</h3>
<table>
<thead>
<tr>
<th>场景</th>
<th>推荐方式</th>
</tr>
</thead>
<tbody>
<tr>
<td>服务主配置</td>
<td><code>spring.config.import</code></td>
</tr>
<tr>
<td>多服务公共配置</td>
<td><code>shared-configs</code></td>
</tr>
<tr>
<td>服务专属附加配置</td>
<td><code>extension-configs</code> 或 <code>spring.config.import</code></td>
</tr>
</tbody>
</table>
<blockquote>
<p><strong><code>shared-configs</code>的<code>refresh</code>必须显式设为<code>true</code></strong>：默认不开启刷新，即使Nacos中的共享配置变更了，应用也不会感知。这一点与<code>spring.config.import</code>导入的DataId默认支持刷新不同。</p>
</blockquote>

<h2 id="小结">小结</h2>
<p>本节课我们学习了：</p>
<ol>
<li><strong>配置中心三级模型</strong>：Namespace → Group → DataId，与服务注册的三级模型层级相同但用法不同；三者共同定位唯一一份配置。</li>
<li><strong>DataId默认构成</strong>：<code>prefix</code> - <code>profile</code> - <code>file-extension</code>；profile为空时整段消失；<code>spring.config.import</code>可以显式指定DataId，跳过默认拼接。</li>
<li><strong>多环境隔离的两种方案</strong>：Namespace隔离（数据物理隔离、权限可细分、推荐用于长期环境）vs DataId隔离（Namespace数量少、便于对比、推荐用于临时验证）。</li>
<li><strong><code>shared-configs</code>与<code>extension-configs</code></strong>：前者用于多服务公共配置，后者用于服务专属附加配置</li>
<li><strong>多环境实战</strong>：通过<code>${NACOS_NAMESPACE:dev}</code>环境变量切换Namespace，DataId不变而配置内容不同。</li>
<li><strong>共享配置实战</strong>：将MyBatis-Plus全局配置抽取到<code>common-mybatis.yml</code>，两个服务通过<code>shared-configs</code>引入，一处修改、两处生效。</li>
<li><strong>本地覆盖实战</strong>：导入<code>-local.yml</code>专用DataId，实现个人调试不影响团队配置。</li>
</ol>
