<h2 id="回顾与导入">回顾与导入</h2>
<p>前面我们验证了Feign与LoadBalancer的集成，并配置<code>spring.cloud.loadbalancer.nacos.enabled=true</code>启用了Nacos权重感知。当时使用的<code>NacosLoadBalancer</code>内部是<strong>加权随机</strong>算法——每次请求独立地按权重概率抽取一个实例。</p>
<p>更根本地，负载均衡算法本身是一组<strong>独立于框架的调度策略</strong>。Spring Cloud LoadBalancer只内置了轮询和随机两种，加权随机来自<code>NacosLoadBalancer</code>。理解这些算法的原理和边界，才能在遇到“流量不均”“会话丢失”“灰度比例不准”等问题时，知道该换哪种算法，或者该写一个什么样的自定义策略。</p>
<p>本节先讲算法原理和框架边界，再落地验证轮询与随机两种内置策略。自定义策略的开发流程与平滑加权轮询的手写实现，将在下一节展开。</p>

<h3 id="常见负载均衡算法">常见负载均衡算法</h3>
<h4 id="简单轮询">简单轮询</h4>
<p><strong>原理：</strong> 用一个计数器记录当前请求序号，通过取模运算得到实例下标。</p>
<div class="codehilite"><pre><span></span><code>index = counter++ % instanceCount
</code></pre></div>

<p>普通轮询的取模算法非常直接：通过原子计数器记录当前请求的序列号，然后对集群节点总数取模，得到具体下标，再从列表取实例。具体实现方式可以参考《OpenFeign与LoadBalancer集成》讲中内容</p>
<table>
<thead>
<tr>
<th>优点</th>
<th>缺点</th>
</tr>
</thead>
<tbody>
<tr>
<td>实现简单，绝对均匀</td>
<td>不感知实例性能差异，性能弱的实例和性能强的实例承受相同流量</td>
</tr>
</tbody>
</table>
<h4 id="加权轮询">加权轮询</h4>
<p><strong>原理：</strong> 为每个实例配置权重，权重高的实例在一次“大轮次”中被连续选中多次。</p>
<p>例如权重 <code>A:4, B:2, C:6</code>，一种基础实现会在一轮中产生 <code>A,A,A,A,B,B,C,C,C,C,C,C</code> 的序列。这种实现的问题是<strong>权重偏差越大，偏移越严重</strong>——高权重实例在一轮的前段被集中选中，后段完全闲置，流量分布很不平滑。</p>
<h4 id="随机与加权随机">随机与加权随机</h4>
<p><strong>随机：</strong> 每次请求从实例列表中随机选一个。实现最简单，长期看分布均匀，但<strong>短期波动大</strong>。</p>
<p><strong>加权随机：</strong> 每次请求独立地按权重比例抽取。常见实现是“区间法”：</p>
<ol>
<li>计算所有健康实例的权重总和 <code>totalWeight</code></li>
<li>为每个实例生成一个累积区间 <code>[cumulative, cumulative + weight)</code></li>
<li>生成 <code>[0, totalWeight)</code> 的随机数，用二分查找定位落在哪个区间</li>
</ol>
<p>Nacos的加权随机实现正是基于这一思路：生成<code>[0~1]</code>范围的随机数，通过二分法查找递增数组<code>weights[]</code>接近的index，再从注册节点列表中返回节点；非健康节点或权重≤0的实例不会被选择。关于加权随机算法的参考实现方法可以参考《Nacos权重路由》讲中<code>WeightedInstanceSelector</code>类的实现。</p>
<h4 id="一致性哈希">一致性哈希</h4>
<p><strong>原理：</strong> 将哈希值空间组织成一个<code>0 ~ 2^32-1</code>的圆环，将实例（通过IP或IP+端口）哈希到环上，将请求（通过某个特征，如用户ID、sessionId）也哈希到环上，然后<strong>顺时针找到第一个实例</strong>。</p>
<p><img loading="lazy" src="/ai-course-site/spring-cloud/assets/ch21/image-20261102214930855.png" alt="image-20261102214930855" style="zoom: 20%;" /></p>
<p><strong>虚拟节点：</strong> 如果每个物理实例只在环上占一个点，实例数量少时容易出现<strong>数据倾斜</strong>——大量请求落在同一个实例上。解决方案是为每个物理实例生成多个虚拟节点，均匀分散在环上。</p>
<p>一致性哈希的核心价值是<strong>最小化节点变动的影响</strong>：当某个实例下线时，只有落在该实例及其虚拟节点上的请求会被重新路由，其他请求不受影响。这正是它适合<strong>有状态服务、缓存、WebSocket长连接</strong>的原因。</p>
<table>
<thead>
<tr>
<th>优点</th>
<th>缺点</th>
</tr>
</thead>
<tbody>
<tr>
<td>请求粘性，相同特征稳定路由</td>
<td>实现复杂度高</td>
</tr>
<tr>
<td>节点变动影响范围小</td>
<td>需要设计合适的哈希特征</td>
</tr>
<tr>
<td>通过虚拟节点解决倾斜</td>
<td>虚拟节点过多会增加内存和查找开销</td>
</tr>
</tbody>
</table>

</blockquote>
<h3 id="重启并验证">重启并验证</h3>
<p>重启book-order，连续调用Feign接口10次：</p>
<div class="codehilite lang-http"><pre><span></span><code><span class="err">GET {{order_url}}/api/order/product/1</span>
</code></pre></div>

<p>预期输出：可能出现连续两次甚至三次同一实例。10次中8081和8082各约5次，但<strong>顺序不可预测</strong>。</p>
<h3 id="通过LoadBalanced-RestTemplate验证">通过@LoadBalanced RestTemplate验证</h3>
<p>随机策略同样对<code>@LoadBalanced RestTemplate</code>生效——因为<code>LoadBalancerLifecycle</code>和<code>ReactorLoadBalancer</code>都是服务名级别的子上下文，与调用方式无关：</p>
<div class="codehilite lang-http"><pre><span></span><code><span class="err">GET {{order_url}}/api/order/product/lb/1</span>
</code></pre></div>

<p>连续调用10次，<code>[LB选中实例]</code>同样呈现随机分布。</p>
<h3 id="只影响book-product">只影响book-product</h3>
<p>通过<code>@LoadBalancerClient(name = "book-product", ...)</code>绑定的策略，<strong>只对book-product生效</strong>。book-order如果还调用book-user，book-user仍然使用默认轮询：</p>
<div class="codehilite lang-java"><pre><span></span><code><span class="c1">// book-user的Feign客户端，未绑定自定义策略</span>
<span class="nd">@FeignClient</span><span class="p">(</span><span class="n">name</span><span class="w"> </span><span class="o">=</span><span class="w"> </span><span class="s">"book-user"</span><span class="p">)</span>
<span class="kd">public</span><span class="w"> </span><span class="kd">interface</span> <span class="nc">UserClient</span><span class="w"> </span><span class="p">{</span><span class="w"> </span><span class="p">...</span><span class="w"> </span><span class="p">}</span>
</code></pre></div>

<p>调用book-user时，<code>[LB选中实例]</code>仍然严格交替（如果book-user有两个实例）。</p>
<h3 id="多个服务使用不同策略">多个服务使用不同策略</h3>
<p>如果book-product用随机、book-user用轮询（默认），只需要为book-product绑定<code>RandomLoadBalancerConfig</code>，book-user不做任何配置。如果需要为多个服务分别指定策略，使用<code>@LoadBalancerClients</code>：</p>
<div class="codehilite lang-java"><pre><span></span><code><span class="nd">@LoadBalancerClients</span><span class="p">({</span>

<span class="w">    </span><span class="nd">@LoadBalancerClient</span><span class="p">(</span><span class="n">name</span><span class="w"> </span><span class="o">=</span><span class="w"> </span><span class="s">"book-user"</span><span class="p">,</span><span class="w"> </span><span class="n">configuration</span><span class="w"> </span><span class="o">=</span><span class="w"> </span><span class="n">SomeOtherConfig</span><span class="p">.</span><span class="na">class</span><span class="p">)</span>
<span class="p">})</span>
</code></pre></div>

<h2 id="轮询与随机的对比分析">轮询与随机的对比分析</h2>
<table>
<thead>
<tr>
<th>场景</th>
<th>推荐策略</th>
<th>理由</th>
</tr>
</thead>
<tbody>
<tr>
<td>实例性能完全一致，追求绝对均匀</td>
<td><strong>轮询</strong></td>
<td>严格交替，无短期偏差</td>
</tr>
<tr>
<td>实例性能有差异，需要按权重分配</td>
<td>加权随机或平滑加权轮询（下一节）</td>
<td>单纯轮询/随机不感知权重</td>
</tr>
<tr>
<td>灰度发布，新版本需要稳定比例</td>
<td><strong>平滑加权轮询</strong></td>
<td>短期也保持比例，不出现“全旧版本”或“全新版本”的窗口</td>
</tr>
<tr>
<td>无状态服务，实例随时扩缩容</td>
<td><strong>随机</strong></td>
<td>无状态，扩缩容时不需要维护计数器；短期波动可接受</td>
</tr>
<tr>
<td>客户端数量极多，避免“惊群”</td>
<td><strong>随机</strong></td>
<td>大量客户端同时按轮询会形成“同步节拍”，随机可以打散</td>
</tr>

<h2 id="注意事项和小节">注意事项和小节</h2>
<ol>
<li>
<p><strong>默认是轮询，不是随机</strong>：Spring Cloud LoadBalancer的默认策略是<code>RoundRobinLoadBalancer</code>。验证前先确认没有其他配置覆盖默认行为。而加权随机由<code>NacosLoadBalancer</code>提供</p>
</li>
<li>
<p><strong>随机策略需要显式绑定</strong>：通过<code>RandomLoadBalancerConfig</code> + <code>@LoadBalancerClient</code>切换。没有配置项可以“一键切换为随机”。</p>
</li>
<li>
<p><strong>配置类不加<code>@Configuration</code></strong>：加了会导致策略全局生效，影响所有服务。</p>
</li>
<li>
<p><strong><code>@LoadBalancerClient</code>的name必须精确匹配</strong>：必须与<code>@FeignClient</code>的<code>name</code>或<code>@LoadBalanced</code>调用的服务名完全一致。</p>
</li>
<li>
<p><strong>关闭缓存再做实验</strong>：<code>cache.enabled: false</code>，否则35秒的缓存会干扰观察。</p>
</li>
<li>
<p><strong>Feign和RestTemplate共享策略</strong>：同一服务名的子上下文是共享的，切换策略后两种调用方式同时生效，不需要分别配置。</p>
</li>
<li>
<p><strong>轮询的“绝对均匀”有前提</strong>：两个实例健康状态相同、权重相同、未启用Nacos权重感知。任一条件不满足，轮询序列都会被打破。</p>
</li>
</ol>
