<h2 id="回顾与导入">回顾与导入</h2>
<p>上一节我们完成了自定义负载均衡的五步开发流程，以平滑加权轮询为例，实现了“按权重分配流量”。但权重解决的是<strong>版本内部</strong>的流量分配问题——例如v1版本的两个实例之间如何分流量。</p>
<p>灰度发布要解决的是另一个问题：<strong>不同版本之间</strong>的流量分配。</p>
<blockquote>
<p><strong>场景：</strong> book-product发布了v2版本，新增了“按分类搜索”的功能。直接全量上线风险太大——如果v2有隐藏bug，所有用户都会受影响。更安全的做法是：先让<strong>1%的内部用户</strong>使用v2，观察一段时间无异常后，逐步扩大到10%、50%，最后全量切换。这个过程就是灰度发布。</p>
</blockquote>
<p>灰度发布有多种实现方式：</p>
<table>
<thead>
<tr>
<th>方式</th>
<th>原理</th>
<th>局限</th>
</tr>
</thead>
<tbody>
<tr>
<td>按IP灰度</td>
<td>白名单指定IP走v2</td>
<td>无法按用户维度精细控制</td>
</tr>
<tr>
<td>按用户ID灰度</td>
<td>用户ID取模决定走哪个版本</td>
<td>需要修改业务代码或路由逻辑</td>
</tr>
<tr>
<td><strong>标签化负载均衡</strong></td>
<td><strong>请求Header携带标签，负载均衡器按标签过滤实例</strong></td>
<td>需要网关/前端配合传递Header</td>
</tr>
<tr>
<td>按流量比例灰度</td>
<td>负载均衡器按比例随机分配</td>
<td>无法控制“哪些用户”进入灰度</td>
</tr>
</tbody>
</table>
<p>本节采用<strong>标签化负载均衡</strong>：在请求Header中携带一个灰度标签（如<code>X-Gray-Tag: v2</code>），自定义负载均衡器读取该标签，从实例列表中<strong>只保留与标签匹配的实例</strong>，再在匹配的实例中做加权选择。如果标签为空或没有匹配实例，则<strong>降级到全部实例</strong>。</p>
<div class="codehilite lang-mermaid"><pre><span></span><code>flowchart TB
    A[请求&lt;br/&gt;X-Gray-Tag: v2] --&gt; B[自定义LoadBalancer]
    B --&gt; C{读取标签}
    C --&gt;|有标签| D[过滤出v2实例]
    C --&gt;|无标签| E[使用全部实例]
    D --&gt; F{过滤结果为空?}
    F --&gt;|否| G[在v2实例中加权选择]
    F --&gt;|是| E
    E --&gt; H[在全部实例中加权选择]

    style G fill:#e8f5e9
    style H fill:#fff3e0
</code></pre></div>

<h2 id="灰度发布核心概念">灰度发布核心概念</h2>
<h3 id="灰度发布的阶段划分">灰度发布的阶段划分</h3>
<p>一次完整的灰度发布通常包含五个阶段：</p>
<table>
<thead>
<tr>
<th>阶段</th>
<th>流量分配</th>
<th>目的</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>阶段一：部署新版本</strong></td>
<td>v2接收0%流量</td>
<td>新版本实例启动并注册，但不接收业务流量</td>
</tr>
<tr>
<td><strong>阶段二：小范围灰度</strong></td>
<td>v2接收1%~5%流量（内部用户）</td>
<td>观察新版本的核心指标、错误日志</td>
</tr>
<tr>
<td><strong>阶段三：扩大灰度</strong></td>
<td>v2接收10%~50%流量</td>
<td>逐步验证新版本在更大流量下的稳定性</td>
</tr>
<tr>
<td><strong>阶段四：全量切换</strong></td>
<td>v2接收100%流量</td>
<td>新版本成为唯一版本</td>
</tr>
<tr>
<td><strong>阶段五：旧版本下线</strong></td>
<td>v1下线</td>
<td>释放资源</td>
</tr>
</tbody>
</table>
<p>每个阶段都需要<strong>可观测的验证指标</strong>：错误率、响应延迟、关键业务指标。如果任一指标异常，应立即回滚——将灰度标签撤销，所有流量回到v1。</p>
<h3 id="标签化负载均衡的定位">标签化负载均衡的定位</h3>
<p>标签化负载均衡是“按规则路由”的一种实现：</p>
<table>
<thead>
<tr>
<th>维度</th>
<th>权重/轮询/随机</th>
<th>标签化负载均衡</th>
</tr>
</thead>
<tbody>
<tr>
<td>路由依据</td>
<td>实例的权重、顺序</td>
<td><strong>请求的特征</strong>（Header）</td>
</tr>
<tr>
<td>流量分配粒度</td>
<td>无差别</td>
<td>可按用户、按场景精细控制</td>
</tr>
<tr>
<td>典型场景</td>
<td>版本内部负载均衡</td>
<td><strong>版本之间的灰度路由</strong></td>
</tr>
</tbody>
</table>
<p>它与上一节自定义策略是<strong>互补关系</strong>：标签化负载均衡负责“选哪个版本”，加权轮询负责“版本内选哪个实例”。在本节的实现中，两者会组合使用——<strong>先按标签过滤，再在过滤结果中做加权选择</strong>。</p>
<h2 id="标签化负载均衡的核心原理">标签化负载均衡的核心原理</h2>
<h3 id="实例标签Nacos元数据">实例标签：Nacos元数据</h3>
<p>实例标签通过Nacos的<strong>实例元数据（metadata）</strong> 实现。在第7节注册服务时，我们已经配置过<code>metadata</code>：</p>

</code></pre></div>

<p>灰度发布中，用<code>metadata</code>的某个键（如<code>version</code>）标识实例的版本：</p>

</blockquote>
<h3 id="请求标签Header">请求标签：Header</h3>
<p>请求标签通过HTTP Header传递。命名建议：</p>
<table>
<thead>
<tr>
<th>Header</th>
<th>用途</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>X-Gray-Tag</code></td>
<td>灰度标签（本节使用）</td>
</tr>
<tr>
<td><code>X-User-Id</code></td>
<td>用户ID（可结合灰度规则计算标签）</td>
</tr>
<tr>
<td><code>X-Gray-Version</code></td>
<td>目标版本号</td>
</tr>
</tbody>
</table>
<p>本节的约定：请求Header <code>X-Gray-Tag</code> 的值表示“希望路由到的版本”。例如<code>X-Gray-Tag: v2</code>表示希望走v2实例。</p>
<h3 id="匹配与降级逻辑">匹配与降级逻辑</h3>
<p>负载均衡器的核心逻辑：</p>
<div class="codehilite lang-mermaid"><pre><span></span><code>flowchart TB
    A[获取实例列表] --&gt; B[读取请求Header X-Gray-Tag]

    C --&gt;|非空| E[过滤 metadata.version == 标签 的实例]
    E --&gt; F{过滤结果是否为空?}
    F --&gt;|非空| G[在过滤结果中做加权选择]

    D --&gt; H[在全部实例中做加权选择]

    style H fill:#fff3e0
</code></pre></div>

<p><strong>降级设计要点：</strong></p>
<table>
<thead>
<tr>
<th>降级场景</th>
<th>处理方式</th>
<th>理由</th>
</tr>
</thead>
<tbody>
<tr>
<td>请求未携带<code>X-Gray-Tag</code></td>
<td>使用全部实例</td>
<td>普通用户不感知灰度，正常走默认流量</td>
</tr>
<tr>

</tr>
<tr>
<td>灰度实例全部不健康</td>
<td>过滤后为空，降级到全部实例</td>
<td>同上的容错逻辑</td>
</tr>
</tbody>
</table>

<h2 id="实现标签化负载均衡器">实现标签化负载均衡器</h2>
<h3 id="完整实现">完整实现</h3>
<p>标签化负载均衡器的核心是：<strong>读取Header标签 → 过滤实例 → 在过滤结果中做加权选择</strong>。本节在过滤之后复用上一节的平滑加权轮询逻辑作为最终选择器。</p>
<div class="codehilite lang-java"><pre><span></span><code><span class="kd">public</span><span class="w"> </span><span class="kd">class</span> <span class="nc">GrayTagLoadBalancer</span><span class="w"> </span><span class="kd">implements</span><span class="w"> </span><span class="n">ReactorServiceInstanceLoadBalancer</span><span class="w"> </span><span class="p">{</span>

<span class="w">    </span><span class="cm">/** 请求头中的灰度标签 */</span>

<h2 id="端到端验证">端到端验证</h2>
<h3 id="验证一无标签请求走全部实例">验证一：无标签请求走全部实例</h3>
<p>不带<code>X-Gray-Tag</code>调用10次：</p>
<div class="codehilite lang-http"><pre><span></span><code><span class="err">### 无灰度标签，应在v1和v2之间按权重分配</span>
<span class="err">GET {{order_url}}/api/order/product/1</span>
</code></pre></div>

<p><strong>预期输出：</strong></p>
<div class="codehilite"><pre><span></span><code>[GRAY] 选中 127.0.0.1:8081 version=v1
[GRAY] 选中 127.0.0.1:8082 version=v2
[GRAY] 选中 127.0.0.1:8081 version=v1
[GRAY] 选中 127.0.0.1:8082 version=v2
...
</code></pre></div>

<p><strong>结论：</strong> 无标签时，普通用户按默认策略在v1/v2之间分配。<strong>灰度阶段一的“0%流量”目标</strong>，可以通过在灰度期间<strong>不配置无标签请求的路由规则</strong>，或者<strong>只在特定Header下才路由到v2</strong>实现——本节的无标签请求会自然分配到v2，这是“阶段四全量切换”之前需要注意的风险点。</p>
<blockquote>
<p><strong>阶段一的正确做法：</strong> 在灰度初期，如果不想让普通用户进入v2，需要在负载均衡器中<strong>进一步限制</strong>——例如只有<code>X-Gray-Tag: v2</code>时才允许选中v2，无标签请求<strong>只使用v1实例</strong>。这需要修改<code>extractGrayTag</code>为空的处理逻辑：空标签时过滤掉v2实例。本节为了演示“标签化”的通用性，采用“无标签走全部实例”的逻辑；生产环境可根据阶段需求调整。</p>
</blockquote>

<h2 id="注意事项">注意事项</h2>
<ol>
<li>
<p><strong>标签化负载均衡只负责“路由”，不负责“决定谁进灰度”</strong>：灰度用户范围的判定（内部用户、1%比例）通常在网关层完成，负载均衡器只按Header路由。</p>
</li>
<li>
<p><strong>降级逻辑是灰度安全的底线</strong>：标签无匹配、灰度实例故障时，必须降级到全部实例，避免灰度用户不可用。</p>
</li>
<li>
<p><strong>无标签请求的默认路由要按阶段调整</strong>：灰度初期应只允许v1，全量切换后才允许v2。本节演示的“无标签走全部实例”适用于全量切换后的阶段。</p>
</li>
<li>
<p><strong>元数据键和Header名要统一</strong>：负载均衡器、实例配置、网关三处必须使用相同的键名，否则路由静默失效。</p>
</li>
<li>
<p><strong>灰度不是“只上不下”</strong>：每个灰度阶段都要有明确的回滚预案——撤销标签是最快的回滚方式。</p>
</li>
</ol>
<h2 id="小结">小结</h2>
<p>本节课我们学习了：</p>
<ol>
<li><strong>灰度发布的核心概念</strong>：五个阶段（部署、小范围灰度、扩大灰度、全量切换、旧版本下线），每个阶段都需要可观测的验证指标和回滚预案。</li>
<li><strong>标签化负载均衡的定位</strong>：按请求Header路由，与权重/轮询等“版本内负载均衡”互补。</li>
<li><strong>实例标签</strong>：通过Nacos元数据<code>metadata.version</code>标识实例版本（v1/v2）。</li>
<li><strong>请求标签</strong>：通过<code>X-Gray-Tag</code> Header传递灰度意图。</li>
<li><strong>标签化负载均衡器的实现</strong>：读取Header → 按<code>metadata.version</code>过滤实例 → 过滤结果为空时降级到全部实例 → 在候选实例中做平滑加权选择。</li>
<li><strong>降级策略</strong>：无标签、标签无匹配、灰度实例故障，三种场景都降级到全部实例，保证业务可用性。</li>
<li><strong>端到端验证</strong>：无标签走全部、<code>v2</code>标签走v2、<code>v1</code>标签走v1、<code>v3</code>标签降级、v2故障时降级。</li>
</ol>
