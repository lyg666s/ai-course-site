Spring Cloud LoadBalancer快速上手

Spring Cloud LoadBalancer快速上手

课程目标

  • 理解@LoadBalanced注解的定位：一个“标记”，而不是负载均衡的实现本身
  • 掌握@LoadBalanced RestTemplate的配置方法和调用方式
  • 理解LoadBalancerInterceptor在请求发出前的“替换host”机制
  • 掌握BlockingLoadBalancerClient与LoadBalancerClientFactory的协作关系
  • 掌握ServiceInstanceListSupplier的默认装配与自定义扩展方式
  • 理解@LoadBalanced RestTemplate与OpenFeign两种调用方式在LoadBalancer层面的异同
  • 完成book-order通过@LoadBalanced RestTemplate调用book-product多实例的验证

回顾与导入

到目前为止，book-order中真正在用的调用方式始终是OpenFeign——BookClient的@FeignClient(name = "book-product")在底层自动完成了服务发现和负载均衡。

如果不使用OpenFeign，有没有更轻量的方式让RestTemplate也具备“用服务名调服务”的能力？答案是@LoadBalanced注解：

@Bean
@LoadBalanced
public RestTemplate restTemplate() {
    return new RestTemplate();
}

// 调用时直接使用服务名
restTemplate.getForObject("http://book-product/api/products/1", Result.class);

这段代码的“神奇”之处在于：book-product并不是一个可解析的域名，但请求却成功了。真正完成“服务名→实例地址”转换的，是@LoadBalanced注解背后隐式注册的拦截器。

本节的核心任务是：把@LoadBalanced从“魔法”拆解成“机制”，理解它为什么能让RestTemplate具备负载均衡能力，以及在什么场景下应该选择它、什么场景下应该继续用OpenFeign。

@LoadBalanced是什么：一个标记，而不是实现

注解本身“什么也没做”

查看@LoadBalanced的源码，会发现它极其简单：

@Target({ ElementType.FIELD, ElementType.PARAMETER, ElementType.METHOD })
@Retention(RetentionPolicy.RUNTIME)
@Documented
@Inherited
@Qualifier
public @interface LoadBalanced {
}

注解上没有任何“负载均衡算法”的实现逻辑。它的本质是一个标记注解，配合@Qualifier使用，作用是告诉Spring：这个RestTemplate Bean需要被负载均衡基础设施“加工”一下。

官方文档对这一点的表述非常直接：@LoadBalanced注解会为RestTemplate添加一个LoadBalancerInterceptor。真正干活的是拦截器，不是注解。

没有@LoadBalanced时会发生什么

如果不加@LoadBalanced，RestTemplate就是一个普通的HTTP客户端：

// 没有 @LoadBalanced
restTemplate.getForObject("http://book-product/api/products/1", Result.class);

请求发出前，RestTemplate会尝试把book-product当作一个真实的主机名去解析。由于book-product不是可解析的域名，会抛出UnknownHostException。这与手动拼接http://127.0.0.1:8081/...的方式在本质上是不同的——手动拼接时，URL中已经是真实的IP和端口。

加了@LoadBalanced之后发生了什么

@LoadBalanced标记的Bean会被Spring Cloud LoadBalancer的自动配置识别并增强：为这个RestTemplate添加LoadBalancerInterceptor。当RestTemplate发出请求时，拦截器在请求真正发出之前介入：

sequenceDiagram
    participant App as book-order代码
    participant RT as RestTemplate
    participant Interceptor as LoadBalancerInterceptor
    participant LBC as BlockingLoadBalancerClient
    participant Nacos as Nacos
    participant Product as book-product实例

    App->>RT: getForObject("http://book-product/api/products/1")
    RT->>Interceptor: 拦截请求
    Interceptor->>LBC: execute("book-product", request)
    LBC->>LBC: LoadBalancer选实例
    LBC->>Nacos: 获取实例列表（或读缓存）
    Nacos-->>LBC: 返回 8081, 8082
    LBC-->>Interceptor: 选中 127.0.0.1:8081
    Interceptor->>RT: 将URL中的book-product替换为127.0.0.1:8081
    RT->>Product: GET http://127.0.0.1:8081/api/products/1
    Product-->>RT: 返回响应

关键点：LoadBalancerInterceptor拦截请求后，把服务名book-product委托给LoadBalancerClient去解析。BlockingLoadBalancerClient根据服务名选出一个ServiceInstance，拦截器再把原URL中的book-product替换为该实例的host:port，最后RestTemplate用替换后的URL发出真实请求。

核心组件：谁在真正做决策

核心组件

LoadBalancerInterceptor

LoadBalancerInterceptor实现了ClientHttpRequestInterceptor，是@LoadBalanced RestTemplate实现负载均衡的入口。它的职责很单一：在请求发出前，把“服务名host”替换为“实例host”。具体选哪个实例，它不负责，而是委托给LoadBalancerClient。

BlockingLoadBalancerClient

BlockingLoadBalancerClient是LoadBalancerClient接口的阻塞式实现，专用于RestTemplate这类同步调用。它内部持有LoadBalancerClientFactory，根据服务名获取对应的ReactorLoadBalancer，执行实例选择，然后把结果返回给拦截器。

LoadBalancerClientFactory：每个服务一个子上下文

LoadBalancerClientFactory是NamedContextFactory的实现，它为每个服务名创建独立的Spring子上下文。这意味着：

能力 说明
策略隔离 book-product的负载均衡策略不会影响book-user
配置隔离 通过@LoadBalancerClient为不同服务指定不同的配置类

ServiceInstanceListSupplier：实例列表的来源

ReactorLoadBalancer不直接访问Nacos，它从ServiceInstanceListSupplier获取实例列表。Spring Cloud LoadBalancer提供了基于DiscoveryClient的实现，从Nacos获取可用实例。

组件结构图

flowchart TD
    A["RestTemplate<br/>@LoadBalanced"] -->|"注册拦截器"| B["LoadBalancerInterceptor<br/>职责：服务名 → 实例地址"]
    B -->|"委托选实例"| C["BlockingLoadBalancerClient<br/>LoadBalancerClient 阻塞式实现"]

    C -->|"按服务名获取"| D["LoadBalancerClientFactory<br/>NamedContextFactory"]
    D -->|"每个服务名<br/>独立子上下文"| E["ReactorLoadBalancer<br/>（book-product 专属策略）"]
    D -->|"每个服务名<br/>独立子上下文"| E2["ReactorLoadBalancer<br/>（book-user 专属策略）"]

    E -->|"获取实例列表"| F["ServiceInstanceListSupplier"]
    E2 --> F
    F -->|"适配"| G["DiscoveryClient<br/>Nacos 实现"]
    G -->|"查询"| H[("Nacos 注册中心")]

    E -.->|"返回 ServiceInstance"| C
    C -.->|"返回 ServiceInstance"| B
    B -->|"重写 URI 后放行"| I["目标服务实例"]
阶段 组件 做什么 不做什么
① 拦截 LoadBalancerInterceptor 提取服务名，触发选实例 不负责选择算法
② 获取 LB BlockingLoadBalancerClient + LoadBalancerClientFactory 按 serviceId 拿到专属子上下文的 ReactorLoadBalancer 不持有实例列表
③ 选实例 ReactorLoadBalancer + ServiceInstanceListSupplier 拉列表 + 按策略选一个 不直接访问 Nacos（由 DiscoveryClient 适配）
④ 改写放行 LoadBalancerInterceptor 把 http://book-product 换成 http://ip:port 不参与业务请求处理

核心要点：LoadBalancerClientFactory 作为 NamedContextFactory，是"策略隔离"的关键——每次 getInstance(serviceId) 都会为对应服务创建/复用一个 Spring 子上下文，从而让 book-product 和 book-user 的负载均衡策略、配置类互不干扰。

实战：配置@LoadBalanced RestTemplate

步骤一：确认依赖

spring-cloud-starter-loadbalancer已通过OpenFeign的传递依赖引入。确认book-order的pom.xml中spring-boot-starter-web存在（提供RestTemplate）。

步骤二：声明@LoadBalanced Bean

在book-order的配置类中：

@Configuration
public class RestTemplateConfig {

    @Bean
    @LoadBalanced
    public RestTemplate loadBalancedRestTemplate() {
        return new RestTemplate();
    }
}

步骤三：使用服务名调用

在OrderService中注入并使用：

@Service
@RequiredArgsConstructor
public class OrderService {

    private final RestTemplate loadBalancedRestTemplate;

    public ProductDto getProductById(Long productId) {
        String url = "http://book-product/api/products/" + productId;

        ParameterizedTypeReference<Result<ProductDto>> typeRef =
                new ParameterizedTypeReference<>() {};

        ResponseEntity<Result<ProductDto>> response =
                loadBalancedRestTemplate.exchange(url, HttpMethod.GET, null, typeRef);

        Result<ProductDto> result = response.getBody();
        return result.getData();
    }
}

关键点： URL中的host是服务名book-product，不是IP或域名。LoadBalancerInterceptor会把它替换为实际选中的实例地址。

验证：实例可见与负载均衡

让选中的实例可见

Feign日志和RestTemplate的普通日志都不会打印最终选中的IP和端口。复用InstanceLoggingLoadBalancerLifecycle：

@Component
public class InstanceLoggingLoadBalancerLifecycle
        implements LoadBalancerLifecycle<RequestDataContext, ResponseData, ServiceInstance> {

    @Override
    public void onStartRequest(Request<RequestDataContext> request,
                               Response<ServiceInstance> lbResponse) {
        ServiceInstance instance = lbResponse.getServer();
        if (instance != null) {
            System.out.println("[LB选中实例] " + instance.getHost() + ":" + instance.getPort());
        }
    }

    // onStart / onComplete 略
}

说明： LoadBalancerLifecycle对@LoadBalanced RestTemplate和@FeignClient同时生效，因为两者在底层都经过LoadBalancerClientFactory。

与OpenFeign的对比

@LoadBalanced RestTemplate和@FeignClient在LoadBalancer层面是同一套基础设施，但使用方式不同：

维度 @LoadBalanced RestTemplate @FeignClient
调用方式 手动拼接URL，调用getForObject等方法 声明式接口，像本地方法一样调用
负载均衡触发方式 注解标记Bean，自动添加拦截器 Feign内部自动集成LoadBalancer
服务名位置 URL中的host @FeignClient(name = ...)
实例可见 LoadBalancerLifecycle 同左
配置策略 @LoadBalancerClient绑定 同左
适用场景 简单调用、临时验证、无法使用Feign的场景 接口契约清晰、调用点多的场景

选择建议： 如果项目已经全面使用OpenFeign，@LoadBalanced RestTemplate更多用于轻量验证或第三方库强制要求RestTemplate的场景。两者可以共存，但建议团队约定统一的主调用方式，避免维护两套调用风格。

小结

本节课我们学习了：

  1. @LoadBalanced的定位：一个标记注解，本身不包含负载均衡逻辑，作用是让Spring Cloud为RestTemplate添加LoadBalancerInterceptor。

  2. 拦截器机制：LoadBalancerInterceptor在请求发出前，把URL中的服务名替换为LoadBalancerClient选中的实例host:port。

  3. 核心组件协作：LoadBalancerClientFactory（服务级子容器）→ ReactorLoadBalancer（选实例）→ ServiceInstanceListSupplier（提供实例列表）→ BlockingLoadBalancerClient（阻塞式适配RestTemplate）。

  4. @LoadBalanced RestTemplate的配置：@Bean + @LoadBalanced，调用时URL的host写服务名。

  5. 实例可见性：通过LoadBalancerLifecycle观察最终选中的IP和端口，该监听器对RestTemplate和Feign同时生效。

  6. 与OpenFeign的对比：底层共用LoadBalancer，区别在调用方式；@LoadBalanced RestTemplate适合轻量验证和特定场景，OpenFeign适合接口契约清晰的日常调用。
