<h2 id="从单体系统到微服务架构">从单体系统到微服务架构</h2>
<h3 id="单体系统存在的问题">单体系统存在的问题</h3>
<p>在软件技术发展的很长一段时间内，软件系统都表现为一种<strong>单体系统</strong>（也叫单块系统）。所谓单体系统，就是把一个系统所涉及的各个组件都打包成一个一体化结构并进行部署和运行。下图展示了一个典型的单体系统，应用服务器上同时运行着 Web 服务层、业务逻辑层和数据访问层组件，这些组件作为一个整体进行统一的开发、部署和维护。</p>
<p><img loading="lazy" src="/ai-course-site/spring-cloud/assets/ch02/image-20261009154923735.png" alt="image-20261009154923735" style="zoom: 50%;" /></p>
<p>单体架构简单而容易实现，但随着业务扩张、结构变化和用户量增加，其优势逐渐无法适应互联网时代的快速发展，面临越来越多的挑战：</p>
<p><strong>1. 可扩展性差</strong></p>
<p>可扩展性（Extensibility）是指系统在面对业务变更时的灵活性。单体系统对任何一处业务的修改都需要重新构建整个系统并发布。内部没有根据业务结构进行合理拆分，是导致可扩展性低下的主要原因。</p>
<p><strong>2. 可伸缩性差</strong></p>
<p>可伸缩性（Scalability）是指当系统出现性能瓶颈时，通过添加硬件设备来解决问题的难易程度。单体系统的所有程序代码都运行在同一个进程中，内存密集型和 CPU 密集型并存，要求所有服务器都必须有足够的内存和强劲的 CPU。以下图为例，组件 A 的负载达到 80%，需要扩容，但组件 B 和 C 的负载不足 20%，由于打包在同一个运行包中，扩容会导致其他组件利用率更低，造成资源浪费。同时，对于需要保持会话（Session）数据的需求，扩容后如何保持各服务器之间数据一致性也存在较大实现难度。</p>
<p><img loading="lazy" src="/ai-course-site/spring-cloud/assets/ch02/wps1.png" alt="img" style="zoom:50%;" /></p>
<p><strong>3. 代码腐化与缺陷修复成本高</strong></p>
<p>在单体系统中，由于缺乏合理的业务和技术实现边界，随着功能增多，当出现缺陷时，可能引起缺陷的原因组合较多，导致分析、定位、修复缺陷的成本增高。同时，代码结构日益复杂，修复一个缺陷可能引入其他缺陷，在不具备完善持续集成和持续交付能力的情况下，容易陷入“越修越多”的恶性循环。</p>
<h3 id="微服务架构的特性">微服务架构的特性</h3>
<p>软件工程大师 Martin Fowler 在《Microservices》一文中提到，微服务架构具有以下核心特性：</p>
<p><strong>1. 服务组件化</strong></p>
<p>组件（Component）是一种可独立替换和升级的软件单元。服务是一种进程外组件，服务之间利用 HTTP 协议完成交互。服务组件化的主要目的是<strong>服务可以独立部署</strong>。将应用程序拆分成多个服务后，通常只需要重新部署那个改变的服务，而不需要重新部署整个应用。</p>
<p><strong>2. 按业务能力组织服务</strong></p>
<p>微服务架构倾向于围绕业务功能来组织服务，而不是围绕技术能力。团队是跨职能的特征团队（Feature Team），包含用户体验、项目管理和技术研发等所有岗位和技能。每个服务都围绕业务进行构建，并能够独立部署到生产环境。</p>
<p><strong>3. 去中心化治理</strong></p>
<p>微服务团队更喜欢不同的标准。在构建具体服务时，可以根据业务上下文选择合适的语言和工具。微服务架构也崇尚对数据进行分散管理，让每个服务管理自己的数据库。</p>
<p><strong>4. 基础设施自动化</strong></p>
<p>使用微服务架构的团队需要更广泛的依赖基础设施自动化技术，包括持续集成和持续交付等。</p>
<p>此外，微服务架构还需要考虑网络传输的三态性、异构性、数据一致性和服务容错性等分布式系统问题。</p>
<h3 id="微服务架构核心组件">微服务架构核心组件</h3>
<p>微服务架构的核心技术组件包括以下六个方面：</p>
<p><strong>1. 服务治理</strong></p>
<p>服务治理是最关键的技术组件，因为各个微服务需要通过服务治理实现自动化的注册和发现。当服务数量达到一定量级时，需要一个独立的媒介来管理服务的实例，这个媒介就是<strong>服务注册中心</strong>。下图展示了服务注册中心的作用。</p>
<p><img loading="lazy" src="/ai-course-site/spring-cloud/assets/ch02/image-20261009155044056.png" alt="image-20261009155044056" style="zoom: 67%;" /></p>
<p>服务注册中心是保存服务调用所需路由信息的存储仓库，也是服务提供者和消费者进行交互的媒介。主流的微服务框架都基于 Zookeeper、Nacos 等分布式协调工具构建了服务注册中心。</p>
<p><strong>2. 服务路由</strong></p>
<p>当客户端请求到达多服务集群环境时，如何确定由某一台服务器对请求做出响应就是服务路由问题。负载均衡是最常见的一种路由方案，常见的客户端/服务器端负载均衡技术都可以完成服务路由。下图展示了注册中心和负载均衡之间的交互关系。</p>
<p><img loading="lazy" src="/ai-course-site/spring-cloud/assets/ch02/image-20261009155058982.png" alt="image-20261009155058982" style="zoom:67%;" /></p>
<p>此外，还可以采用路由规则（如白名单或黑名单）实现精细化的路由管理。</p>
<p><strong>3. 服务容错</strong></p>
<p>服务容错需要考虑服务自身失败以及依赖其他服务导致的失败。除了超时、重试和异步解耦外，还需要考虑针对各种场景的容错机制。下图展示了服务容错的常见实现策略。</p>
<p><img loading="lazy" src="/ai-course-site/spring-cloud/assets/ch02/image-20261009155111399.png" alt="image-20261009155111399" style="zoom: 67%;" /></p>
<p>包括集群容错策略、服务隔离机制、服务限流机制和服务熔断机制等。Spring Cloud Alibaba 内置了专用的服务可用性框架 Sentinel。</p>
<p><strong>4. 服务网关</strong></p>
<p>服务网关（API 网关）封装了系统内部架构，为每个客户端提供一个定制的 API。在微服务架构中，所有客户端和消费端都通过统一的网关接入微服务，在网关层处理所有非业务功能。下图展示了服务网关的常见功能。</p>
<p><img loading="lazy" src="/ai-course-site/spring-cloud/assets/ch02/image-20261009155124975.png" alt="image-20261009155124975" style="zoom:67%;" /></p>
<p>服务网关可以完成身份验证、监控、缓存、请求管理、静态响应处理等功能，并可以制定灵活的路由策略。Spring Cloud Gateway 是代表性的实现框架。</p>
<p><strong>5. 服务配置</strong></p>
<p>在微服务架构中，由于服务数量和配置信息的分散性，一般需要引入配置中心。配置中心管理的是配置信息而不是服务实例信息。下图展示了配置中心与注册中心之间的交互关系。</p>
<p><img loading="lazy" src="/ai-course-site/spring-cloud/assets/ch02/image-20261009155136062.png" alt="image-20261009155136062" style="zoom:67%;" /></p>
<p>配置中心通常需要依赖分布式协调机制，确保配置信息在分布式环境中的各个服务中得到实时、一致的管理。Nacos 是 Spring Cloud Alibaba 提供的配置中心实现。</p>
<p><strong>6. 服务跟踪</strong></p>
<p>当服务数量达到一定量级时，需要构建分布式服务跟踪机制，解决两个核心问题：如何管理服务之间的调用关系，以及如何跟踪业务流的处理过程和结果。下图展示了分布式服务跟踪相关的核心功能。</p>
<p><img loading="lazy" src="/ai-course-site/spring-cloud/assets/ch02/image-20261009155158088.png" alt="image-20261009155158088" style="zoom:67%;" /></p>
<p>服务跟踪需要完成调用链数据的生成、采集、存储及查询，并对调用链数据进行运算和可视化管理。Spring Cloud 提供了 Spring Cloud Sleuth 与 Zipkin 的集成方案，本课程采用 Micrometer Tracing + OpenTelemetry。</p>

<h2 id="注意事项">注意事项</h2>
<ol>
<li><strong>父模块 packaging 必须为 pom</strong>：否则无法声明子模块。</li>
<li><strong>子模块版本继承</strong>：子模块继承父 POM 的版本，无需单独声明 <code>&lt;version&gt;</code>。</li>
<li><strong>内部模块依赖</strong>：<code>book-common</code> 依赖必须写 <code>${project.version}</code>。</li>
<li><strong>本节课不导入 BOM</strong>：本节课只完成工程骨架搭建。</li>
<li><strong>JDK 版本</strong>：Spring Cloud Alibaba 2025.0.0.0 要求 JDK 17+。</li>
<li><strong>模块命名规范</strong>：公共模块使用 <code>-common</code> 后缀，服务模块使用业务名称。</li>
</ol>
<h2 id="小结">小结</h2>
<p>本节课我们学习了：</p>
<ol>
<li>
<p><strong>单体系统的问题</strong>：可扩展性差、可伸缩性差、代码腐化与缺陷修复成本高。</p>
</li>
<li>
<p><strong>微服务架构的特性</strong>：服务组件化、按业务能力组织服务、去中心化治理、基础设施自动化。</p>
</li>
<li>
<p><strong>微服务架构核心组件</strong>：服务治理、服务路由、服务容错、服务网关、服务配置、服务跟踪。</p>
</li>
<li>
<p><strong>Spring Cloud Alibaba 技术栈</strong>：Nacos、OpenFeign、LoadBalancer、Gateway、RocketMQ、Seata、Sentinel、Micrometer Tracing + OpenTelemetry。</p>
</li>
<li>
<p><strong>多模块工程搭建</strong>：使用 Spring Initializr 创建父工程，配置父 POM 基础信息和子模块 POM，验证编译成功。</p>
</li>
</ol>
