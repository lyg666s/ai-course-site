<h2 id="回顾与导入">回顾与导入</h2>
<p>在前面课程中，我们完成了多模块工程搭建、三个服务的CRUD实现、Spring Cloud Alibaba技术栈的BOM导入，以及公共模块的统一响应与异常体系。此时，三个服务（book-product、book-user、book-order）可以独立运行，但它们之间<strong>无法感知对方的存在</strong>。</p>
<p>来看一个真实的问题场景：</p>
<blockquote>
<p>订单服务创建订单时需要扣减商品库存，但目前订单服务直接接收前端传来的商品信息（title、author、price），并没有真正调用商品服务。即便后续引入了远程调用，订单服务也需要知道商品服务的<strong>具体地址</strong>（IP + 端口）。如果商品服务的地址写死在配置文件中，一旦商品服务扩容或宕机迁移，就需要手动修改配置并重启订单服务，这在微服务环境下是不可接受的。</p>
</blockquote>
<p>这就是<strong>服务注册中心</strong>要解决的核心问题：</p>

<td>服务地址硬编码</td>
<td>服务启动时自动注册到注册中心</td>

<tr>
<td>服务地址动态变化</td>
<td>消费者从注册中心动态获取服务地址</td>

<td>无法感知服务健康状态</td>

<h2 id="为什么选择Nacos">为什么选择Nacos</h2>
<h3 id="主流注册中心对比">主流注册中心对比</h3>
<p>在微服务架构中，常见的服务注册中心方案包括以下几种：</p>
<table>
<thead>
<tr>
<th>注册中心</th>
<th>一致性协议</th>
<th>健康检查</th>
<th>配置中心</th>
<th>控制台</th>
<th>维护方</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>Nacos</strong></td>
<td>AP/CP 可切换</td>
<td>心跳 + 主动探测</td>
<td>支持</td>
<td>内置</td>
<td>阿里巴巴</td>
</tr>
<tr>
<td>Eureka</td>
<td>AP</td>
<td>心跳</td>
<td>不支持</td>
<td>有</td>
<td>Netflix（已停更）</td>
</tr>
<tr>
<td>Consul</td>
<td>CP</td>
<td>多种方式</td>
<td>支持</td>
<td>内置</td>
<td>HashiCorp</td>
</tr>
<tr>
<td>Zookeeper</td>
<td>CP</td>
<td>Session</td>
<td>不支持</td>
<td>无</td>
<td>Apache</td>
</tr>
</tbody>
</table>
<blockquote>
<p>CAP理论：分布式系统的一致性（Consistency）、可用性（Availability）和分区容错性（Partition tolerance）无法同时完全满足，最多只能同时满足其中两个；由于网络分区在分布式系统中通常不可避免，所以一般必须保留分区容错性，而在发生分区时只能在一致性与可用性之间取舍——选择CP会优先保证数据一致，但可能拒绝请求或不可用，选择AP会优先保证服务可用，但可能返回旧数据，因此常见系统如ZooKeeper偏CP，Eureka偏AP。</p>
</blockquote>
<p>Nacos（Dynamic Naming and Configuration Service）在本课程中被选为注册中心，原因如下：</p>
<table>
<thead>
<tr>
<th>优势</th>
<th>说明</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>一站式方案</strong></td>
<td>同时提供注册中心和配置中心能力，本课程后续将技术使用该框架实现配置中心</td>
</tr>
<tr>
<td><strong>生态集成好</strong></td>
<td>Spring Cloud Alibaba 原生集成，与 OpenFeign、Gateway 无缝协作</td>
</tr>
<tr>
<td><strong>生产验证</strong></td>
<td>国内 50%+ 市场份额，被各行业头部企业广泛使用</td>
</tr>
<tr>
<td><strong>AP/CP 可切换</strong></td>
<td>根据业务场景灵活选择一致性模型</td>
</tr>
<tr>
<td><strong>控制台友好</strong></td>
<td>内置可视化管理界面，便于开发和运维</td>
</tr>
</tbody>
</table>
<blockquote>
<p><strong>Nacos 3.x 重要变化：</strong> Nacos 从 3.0.0 版本开始默认启用鉴权功能，控制台端口从 8848 调整为 8080（客户端通信端口仍为 8848）。同时，Nacos 3.x 不再支持 JDK 8，要求 JDK 17+。</p>
</blockquote>
<h3 id="Spring-Cloud-Alibaba-与-Nacos-版本对应">Spring Cloud Alibaba 与 Nacos 版本对应</h3>

<h2 id="注意事项">注意事项</h2>
<ol>
<li>
<p><strong>JDK 版本要求</strong>：Nacos 3.x 要求 JDK 17+，与 Spring Boot 3.5.X 保持一致。如果本机默认 JDK 版本低于 17，需要切换到 JDK 17 后再启动 Nacos。</p>
</li>
<li>
<p><strong>端口冲突</strong>：Nacos 默认使用 8848（客户端通信）和 8080（控制台）端口。Nacos 3.x 的控制台端口为 8080，与 Spring Boot 应用常用的 8080 端口可能冲突，建议后续将 Gateway 的端口调整为其他值（如 8085）。</p>
</li>
<li>
<p><strong>内存配置</strong>：Nacos 运行建议至少 2C4G。如果机器内存不足，可以调整 <code>bin/startup.sh</code> 中的 JVM 参数（如 <code>-Xms512m -Xmx512m</code>）。</p>
</li>
<li>
<p><strong>首次启动输入鉴权配置</strong>：Nacos 3.0.0 开始默认启用鉴权，首次启动时会提示输入三个鉴权相关配置，必须填写才能正常启动。</p>
</li>
<li>
<p><strong>数据持久化</strong>：单机模式默认使用内置 Derby 数据库，数据存储在 <code>${nacos.home}/data/</code> 目录下。重启 Nacos 不会丢失数据，但 Derby 不适合生产环境。</p>
</li>
<li>
<p><strong>不要暴露到公网</strong>：如果未开启鉴权（或鉴权配置较弱），Nacos 控制台不应暴露到公网，应放在可信内部网络中。</p>
</li>
<li>
<p><strong>版本一致性</strong>：Nacos Server 版本应与 Spring Cloud Alibaba 中 Nacos Client 的版本保持一致（本课程为 3.0.3）。</p>
</li>
</ol>
<h2 id="小结">小结</h2>
<p>本节课我们学习了：</p>
<ol>
<li><strong>服务注册中心的作用</strong>：解决微服务架构中服务地址动态变化、服务发现、健康检测等问题。</li>
<li><strong>为什么选择 Nacos</strong>：一站式方案（注册中心 + 配置中心）、生态集成好、生产验证充分、AP/CP 可切换。</li>
<li><strong>版本对应关系</strong>：Spring Cloud Alibaba 2025.0.0.0 对应 Nacos Server 3.0.3。</li>
<li><strong>Nacos 单机版安装</strong>：下载二进制包，解压，使用 <code>startup.cmd -m standalone</code> 启动。</li>
<li><strong>Nacos 3.x 关键变化</strong>：控制台端口改为 8080，默认开启鉴权，要求 JDK 17+。</li>
<li><strong>控制台快速上手</strong>：了解了服务管理、配置管理、命名空间等核心功能模块。</li>
</ol>
