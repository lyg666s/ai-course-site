<table>
<thead>
<tr>
<th>问题</th>
<th>说明</th>
</tr>

<tr>
<td><strong>环境混乱</strong></td>

</tr>

<h2 id="Nacos分级存储模型">Nacos分级存储模型</h2>
<h3 id="三层结构概览">三层结构概览</h3>
<p>Nacos 的分级存储模型是一个基于 <strong>Namespace（命名空间）→ Group（分组）→ Service（服务）</strong> 三大维度的配置管理结构，这三个维度相互独立又彼此配合，为复杂的配置管理提供了灵活的组织方式。</p>
<div class="codehilite lang-mermaid"><pre><span></span><code>flowchart TB
    N[Nacos Server] --&gt; NS1[Namespace: dev]
    N --&gt; NS2[Namespace: test]
    N --&gt; NS3[Namespace: public]

    NS1 --&gt; G1[Group: DEFAULT_GROUP]
    NS1 --&gt; G2[Group: ORDER_GROUP]

    G1 --&gt; D2[Service: book-product]
    G2 --&gt; D3[Service: book-order]

    NS2 --&gt; G3[Group: DEFAULT_GROUP]
    G3 --&gt; D5[Service: book-product]

    style N fill:#e3f2fd
    style NS1 fill:#e8f5e9
    style NS2 fill:#fff3e0
    style NS3 fill:#f3e5f5
</code></pre></div>

<h3 id="三个维度的定位">三个维度的定位</h3>
<table>
<thead>
<tr>
<th>维度</th>
<th>定位</th>
<th>隔离级别</th>
<th>常用场景</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>Namespace</strong></td>
<td>最上层隔离维度，用于区分不同环境或不同租户</td>
<td>逻辑隔离，不同 Namespace 之间的服务和配置完全不可见</td>
<td>dev/test/prod 环境隔离、多租户隔离</td>
</tr>
<tr>
<td><strong>Group</strong></td>
<td>在 Namespace 内进一步分组，用于区分不同业务线或项目</td>
<td>同一 Namespace 内不同 Group 的服务默认不可见</td>
<td>业务线隔离（order-group、pay-group）</td>
</tr>
<tr>
<td><strong>Service</strong></td>
<td>最小单元</td>
<td>标识具体服务</td>
<td>服务名、配置文件名</td>
</tr>
</tbody>
</table>
<blockquote>
<p><strong>记忆口诀：</strong> Namespace 切环境，Group 切业务线，Service 标识具体服务。</p>
</blockquote>
<h3 id="Namespace的隔离机制">Namespace的隔离机制</h3>
<p>Namespace 是 Nacos 用于实现资源逻辑隔离的核心概念。每个 Namespace 拥有自己独立的服务注册表、配置列表和集群信息。其核心特性包括：</p>
<table>
<thead>
<tr>
<th>特性</th>
<th>说明</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>逻辑隔离</strong></td>
<td>不同 Namespace 之间的服务、配置相互不可见</td>
</tr>
<tr>
<td><strong>资源隔离</strong></td>
<td>每个 Namespace 拥有独立的数据存储（逻辑上）</td>
</tr>
<tr>
<td><strong>多租户支持</strong></td>
<td>适合多团队、多项目、多环境场景</td>
</tr>
<tr>
<td><strong>权限控制</strong></td>
<td>可基于 Namespace 进行精细化的权限管理</td>
</tr>
</tbody>
</table>
<p>不同的命名空间下，可以存在相同的 Group 或 Service 的配置。Namespace 的常用场景之一是不同环境的配置的区分隔离，例如开发测试环境和生产环境的资源隔离。</p>
<h3 id="数据模型在服务注册中的体现">数据模型在服务注册中的体现</h3>
<p>Nacos 的服务注册同样遵循三级模型。一个服务的完整标识由 Namespace + Group + ServiceName 组成：</p>
<table>
<thead>
<tr>
<th>层级</th>
<th>示例值</th>
<th>说明</th>
</tr>
</thead>
<tbody>
<tr>
<td>Namespace</td>
<td><code>dev</code></td>
<td>开发环境命名空间 ID</td>
</tr>
<tr>
<td>Group</td>
<td><code>DEFAULT_GROUP</code></td>
<td>默认分组</td>
</tr>
<tr>
<td>ServiceName</td>
<td><code>book-product</code></td>
<td>服务名</td>
</tr>
</tbody>
</table>
<p>这意味着，<strong>即使两个服务名相同（都是 book-product），只要它们在不同的 Namespace 中，就是完全独立的两个服务</strong>，互相不可见。开发环境的 book-order 无法发现测试环境的 book-product，这正是环境隔离的核心机制。</p>

<h2 id="注意事项">注意事项</h2>
<ol>
<li>
<p><strong>namespace 填 ID 而非名称</strong>：这是最常见的错误。<code>namespace</code> 参数必须是命名空间 ID（如 <code>dev</code>），不是命名空间名称（如 <code>开发环境</code>）。</p>
</li>
<li>
<p><strong>Nacos 3.x 默认命名空间变化</strong>：Nacos 3.0 的默认命名空间 ID 为 <code>public</code>，不再是空字符串。</p>
</li>
<li>
<p><strong>Namespace 切环境，Group 切业务线</strong>：推荐的分工方式。不要用 Group 代替 Namespace 做环境隔离，Namespace 的隔离级别更高。我们将在下一讲中介绍 Group 分组机制。</p>
</li>
<li>
<p><strong>同名服务在不同 Namespace 中互相独立</strong>：dev 的 book-product 和 test 的 book-product 是两个完全独立的服务，不会互相发现。</p>
</li>
<li>
<p><strong>metadata 辅助识别</strong>：在 metadata 中添加 <code>env: dev</code> 等标记，便于在控制台中直观区分环境。</p>
</li>
<li>
<p><strong>端口规划</strong>：在同一台机器上运行不同环境的服务时，需要为不同环境分配不同的端口，避免端口冲突。</p>
</li>
</ol>
<h2 id="小结">小结</h2>
<p>本讲我们学习了：</p>
<ol>
<li><strong>Nacos 分级存储模型</strong>：Namespace → Group → Service 三层结构，Namespace 用于环境隔离，Group 用于业务线隔离。</li>
<li><strong>Namespace 的隔离机制</strong>：不同 Namespace 之间的服务和配置完全不可见，实现环境级别的隔离。</li>
<li><strong>Nacos 3.x 的重要变化</strong>：默认命名空间 ID 从空字符串改为 <code>public</code>，以及相关的兼容性注意事项。</li>
<li><strong>控制台创建命名空间</strong>：在 Nacos 控制台的“命名空间”页面创建 dev 和 test 命名空间。</li>
<li><strong>客户端配置命名空间</strong>：通过 <code>spring.cloud.nacos.discovery.namespace</code> 配置，值为命名空间 ID。</li>
<li><strong>环境隔离验证</strong>：通过控制台和 DiscoveryClient 两种方式验证不同命名空间的服务互相隔离。</li>
</ol>
