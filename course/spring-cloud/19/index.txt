<h2 id="一下单扣库存的流程设计">一、下单扣库存的流程设计</h2>
<h3 id="完整业务流程">完整业务流程</h3>
<p>一次下单请求的完整流程如下（一种可能的方案）：</p>
<div class="codehilite lang-mermaid"><pre><span></span><code>sequenceDiagram
    participant Client as 客户端
    participant Order as book-order
    participant Product as book-product
    participant OrderDB as book_order_db

    Client-&gt;&gt;Order: POST /api/orders（userId + items）
    Order-&gt;&gt;Order: 参数校验
    Order-&gt;&gt;OrderDB: 保存订单主表（status=CREATED, total=0）
    loop 每个订单项
        Order-&gt;&gt;Product: Feign getProductById(productId)
        Product--&gt;&gt;Order: 返回ProductDto（真实商品信息）
        Order-&gt;&gt;Product: Feign deductStock(productId, quantity)
        alt 库存充足
            Product--&gt;&gt;Order: 200 扣减成功
        else 库存不足
            Product--&gt;&gt;Order: 1004 库存不足
            Order-&gt;&gt;Order: 抛出BusinessException
            Note over Order,OrderDB: 本地事务回滚
            Order--&gt;&gt;Client: 返回错误
        end
        Order-&gt;&gt;OrderDB: 保存商品快照item
        Order-&gt;&gt;OrderDB: 保存订单明细order_item
    end
    Order-&gt;&gt;OrderDB: 更新订单总金额
    Order--&gt;&gt;Client: 返回OrderDetailVO
</code></pre></div>

<h2 id="三写操作的安全设计">三、写操作的安全设计</h2>
<p><code>createOrder</code>中出现了两次远程调用：<code>getProductById</code>（GET）和<code>deductStock</code>（POST）。两者的安全策略完全不同——GET可以有限重试，POST绝不能重试。本节从<strong>超时</strong>和<strong>重试</strong>两个维度出发，把写操作的远程调用安全边界讲清楚。</p>
<h3 id="31-超时的两个维度">3.1 超时的两个维度</h3>
<p>OpenFeign的超时分为两个层面，分别对应TCP连接建立和响应等待两个阶段：</p>
<table>
<thead>
<tr>
<th>超时类型</th>
<th>参数</th>
<th>含义</th>
<th>触发场景</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>连接超时</strong></td>
<td><code>connectTimeout</code></td>
<td>建立TCP连接的最大等待时间</td>
<td>服务端口未监听、网络不通、防火墙拦截</td>
</tr>
<tr>
<td><strong>读取超时</strong></td>
<td><code>readTimeout</code></td>
<td>连接建立后，从发送请求到接收完响应的最大等待时间</td>
<td>服务端处理慢、数据库慢查询、响应体过大</td>
</tr>
</tbody>
</table>
<p>两者是<strong>串联关系</strong>：连接超时生效于“三次握手”阶段，读取超时生效于“连接已建立、等待数据返回”阶段。</p>
<h3 id="32-超时配置写操作要留足余量">3.2 超时配置：写操作要留足余量</h3>
<p>扣库存的超时需要比查询更谨慎：</p>
<table>
<thead>
<tr>
<th>超时场景</th>
<th>后果</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>超时太短</strong></td>
<td>图书服务可能还在执行，订单服务已判定失败并回滚，但库存可能已被扣减</td>
</tr>
<tr>
<td><strong>超时太长</strong></td>
<td>订单服务线程被长时间阻塞，影响吞吐</td>
</tr>
</tbody>
</table>

<div class="codehilite lang-yaml"><pre><span></span><code><span class="nt">spring</span><span class="p">:</span>
<span class="w">  </span><span class="nt">cloud</span><span class="p">:</span>
<span class="w">    </span><span class="nt">openfeign</span><span class="p">:</span>
<span class="w">      </span><span class="nt">client</span><span class="p">:</span>
<span class="w">        </span><span class="nt">config</span><span class="p">:</span>
<span class="w">          </span><span class="nt">default</span><span class="p">:</span>
<span class="w">            </span><span class="nt">connectTimeout</span><span class="p">:</span><span class="w"> </span><span class="l l-Scalar l-Scalar-Plain">3000</span>
<span class="w">            </span><span class="nt">readTimeout</span><span class="p">:</span><span class="w"> </span><span class="l l-Scalar l-Scalar-Plain">5000</span>
<span class="w">          </span><span class="nt">book-product</span><span class="p">:</span>
<span class="w">            </span><span class="nt">connectTimeout</span><span class="p">:</span><span class="w"> </span><span class="l l-Scalar l-Scalar-Plain">2000</span>
<span class="w">            </span><span class="nt">readTimeout</span><span class="p">:</span><span class="w"> </span><span class="l l-Scalar l-Scalar-Plain">5000</span><span class="w">        </span><span class="c1"># 扣库存是写操作，留足5秒</span>
</code></pre></div>

<blockquote>
<p><strong>按服务而非按方法配置：</strong> Feign的超时是<strong>按服务</strong>配置的，<code>getProductById</code>和<code>deductStock</code>共用同一个<code>readTimeout</code>。如果查询和写操作需要不同超时，需要拆分Feign客户端（使用<code>contextId</code>方案）。</p>
</blockquote>
<h3 id="33-超时与下游P99的关系">3.3 超时与下游P99的关系</h3>
<p>超时配置不是拍脑袋决定的，它应该与下游接口的实际耗时对齐：</p>
<div class="codehilite"><pre><span></span><code>readTimeout ≥ 下游接口的 P99 响应时间
</code></pre></div>

<table>
<thead>
<tr>
<th>接口类型</th>
<th>P99参考</th>
<th>推荐<code>readTimeout</code></th>
</tr>
</thead>
<tbody>
<tr>
<td>查询（<code>getProductById</code>）</td>
<td>200ms</td>
<td>2000ms（留足余量）</td>
</tr>
<tr>
<td>扣库存（<code>deductStock</code>）</td>
<td>500ms</td>
<td>5000ms（写操作更保守）</td>
</tr>
</tbody>
</table>
<blockquote>
<p><strong>超时太长或太短都有问题：</strong> 太短会导致正常请求被误判失败；太长会在下游故障时长时间占用调用方线程。<strong>写操作的超时尤其不能太短</strong>——超时后“库存可能已扣”的不确定性窗口会变大，这正是第四节中要复现的分布式事务问题来源之一。</p>
</blockquote>
<h3 id="34-Spring-Cloud-OpenFeign默认不重试">3.4 Spring Cloud OpenFeign默认不重试</h3>
<p>这是一个容易误解的点：</p>
<table>
<thead>
<tr>
<th>框架</th>
<th>默认重试行为</th>
</tr>
</thead>
<tbody>
<tr>
<td>原生Feign</td>
<td>对IO异常和<code>RetryableException</code>自动重试</td>
</tr>
<tr>
<td><strong>Spring Cloud OpenFeign</strong></td>
<td><strong>默认不重试</strong>（<code>Retryer.NEVER_RETRY</code>）</td>
</tr>
</tbody>
</table>
<p>Spring Cloud OpenFeign默认创建一个<code>Retryer.NEVER_RETRY</code> Bean，<strong>禁用重试</strong>。这意味着：在不做任何重试配置的情况下，调用超时或失败后<strong>立即抛出异常</strong>，不会自动重试。</p>
<p><strong>这对下单扣库存是安全的默认值。</strong> 扣库存是写操作，重试会导致库存被扣两次。</p>
<h3 id="35-重试的安全边界POST禁止重试">3.5 重试的安全边界：POST禁止重试</h3>
<p>重试的前提是<strong>操作可以安全地重复执行</strong>：</p>
<table>
<thead>
<tr>
<th>HTTP方法</th>
<th>是否幂等</th>
<th>重试建议</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>GET</code></td>
<td>是</td>
<td>可以有限重试</td>
</tr>
<tr>
<td><code>PUT</code></td>
<td>是（幂等）</td>
<td>谨慎重试，需确认业务语义</td>
</tr>
<tr>
<td><code>DELETE</code></td>
<td>是（幂等）</td>
<td>谨慎重试，需确认业务语义</td>
</tr>
<tr>
<td><strong><code>POST</code></strong></td>
<td><strong>否</strong></td>
<td><strong>默认禁止重试</strong></td>
</tr>
</tbody>
</table>
<p>如果后续需要为GET查询启用重试，可以引入<code>spring-retry</code>：</p>
<div class="codehilite lang-xml"><pre><span></span><code><span class="nt">&lt;dependency&gt;</span>
<span class="w">    </span><span class="nt">&lt;groupId&gt;</span>org.springframework.retry<span class="nt">&lt;/groupId&gt;</span>
<span class="w">    </span><span class="nt">&lt;artifactId&gt;</span>spring-retry<span class="nt">&lt;/artifactId&gt;</span>
<span class="nt">&lt;/dependency&gt;</span>
</code></pre></div>

<p>并配置LoadBalancer重试：</p>
<div class="codehilite lang-yaml"><pre><span></span><code><span class="nt">spring</span><span class="p">:</span>
<span class="w">  </span><span class="nt">cloud</span><span class="p">:</span>
<span class="w">    </span><span class="nt">loadbalancer</span><span class="p">:</span>
<span class="w">      </span><span class="nt">retry</span><span class="p">:</span>
<span class="w">        </span><span class="nt">enabled</span><span class="p">:</span><span class="w"> </span><span class="l l-Scalar l-Scalar-Plain">true</span>
<span class="w">        </span><span class="nt">max-retries-on-next-service-instance</span><span class="p">:</span><span class="w"> </span><span class="l l-Scalar l-Scalar-Plain">1</span>
<span class="w">        </span><span class="nt">max-retries-on-same-service-instance</span><span class="p">:</span><span class="w"> </span><span class="l l-Scalar l-Scalar-Plain">0</span>
<span class="w">        </span><span class="nt">retry-on-all-operations</span><span class="p">:</span><span class="w"> </span><span class="l l-Scalar l-Scalar-Plain">false</span><span class="w">     </span><span class="c1"># 仅GET重试</span>
</code></pre></div>

<blockquote>
<p><strong>关键点：</strong> <code>retry-on-all-operations</code>默认为<code>false</code>，即<strong>仅对GET请求重试</strong>。不要轻易将其改为<code>true</code>，否则POST扣库存会被重试，导致重复扣减。</p>
</blockquote>
<h3 id="36-幂等性网络层的重复投递">3.6 幂等性：网络层的重复投递</h3>
<p>虽然HTTP层禁止了重试，但网络层仍可能发生重复投递（TCP重传、代理重发）。严格的扣库存接口应该具备<strong>幂等性</strong>——同一笔订单的同一商品，重复扣减只生效一次。</p>
<p><strong>生产环境的常见方案：</strong> 在<code>StockDeductRequest</code>中增加<code>requestId</code>（如订单号+商品ID），图书服务用唯一索引或Redis做去重。</p>
<blockquote>
<p><strong>本节取舍：</strong> 幂等性的完整实现涉及图书服务侧的改造（唯一索引、去重表），超出本节“订单-图书调用”的范围。本节先建立“写操作必须考虑幂等”的意识，具体实现在后续课程或项目中展开。</p>
</blockquote>

<h2 id="小结">小结</h2>
<p>本节课我们学习了：</p>
<ol>
<li><strong>下单扣库存的完整流程</strong>：保存订单主表 → 循环处理订单项（查商品 → 扣库存 → 建快照 → 建明细）→ 更新总金额。</li>
<li><strong>OrderItemRequest的精简</strong>：去掉<code>title</code>、<code>author</code>、<code>price</code>，只保留<code>productId</code>和<code>quantity</code>，商品信息以服务端查询为准，防止用户篡改价格。</li>
<li><strong>OrderServiceImpl的改造</strong>：注入<code>BookClient</code>，用<code>getProductById()</code>查询真实商品信息，用<code>deductStock()</code>扣减真实库存。</li>
<li><strong>超时的两个维度</strong>：<code>connectTimeout</code>（连接建立）和<code>readTimeout</code>（响应等待），必须显式配置，使用新前缀<code>spring.cloud.openfeign.client.config</code>。</li>
<li><strong>Spring Cloud OpenFeign默认不重试</strong>：<code>Retryer.NEVER_RETRY</code>是安全默认值；重试仅对GET开启，POST扣库存禁止重试；</li>
<li><strong>写操作的安全设计</strong>：POST不重试、超时留余量、幂等性意识。</li>
<li><strong>端到端验证的四个场景</strong>：正常下单、库存不足、图书服务不可用、多订单项部分失败。</li>
<li><strong>分布式事务问题的暴露</strong>：本地事务回滚但远程扣减已执行，订单不存在但库存已减少——这是后续Seata要解决的核心问题。</li>
<li><strong>第三部分的收官</strong>：从<code>RestTemplate</code>到OpenFeign，从注解到日志、拦截器、超时重试、负载均衡，最终落地到真实的业务场景。</li>
</ol>
